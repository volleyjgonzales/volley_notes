## 1. What the evidence actually establishes

It does not establish which packets were lost or why the state persisted.
- **Verified—recorded:** E2 had enlarged buffers, zero central `RcvbufErrors`, zero drops on the surviving REST sockets, and continuing failures (F:408–425). **Inferred—high:** Central receive-buffer overflow is **not necessary** for this symptom. “UDP loss isn't the cause” is too broad: these counters do not measure server/bay receive queues, host NIC/veth/VXLAN drops, IP reassembly failure, qdisc/sender loss, failed DDS sends, DDS history exhaustion, or SHM queues. Earlier server counts were zero; that is useful but not an end-to-end loss measurement. Different triggers may converge on the same persistent middleware state.
- **Verified:** rmw 9.4.9's readiness function requires (a) nonzero, equal graph-cache request-reader/response-writer counts and (b) nonzero, equal local DDS match counters. It does **not** report which condition failed. [rmw_service_server_is_available.cpp:79–127](https://github.com/ros2/rmw_fastrtps/blob/9.4.9/rmw_fastrtps_shared_cpp/src/rmw_service_server_is_available.cpp#L79). **Inferred—high:** The stuck process could have a graph-cache inconsistency, one unmatched direction, or unequal counts. A fresh process's clean graph rules out none of those locally. `ros2 service info` also reports that observer's graph, not what the bay process itself has matched. “The server knows the REST API endpoints” must distinguish the discovery server's database from the bay service's local state.
- **Verified:** The timer replaces unmatched clients every 10 s and destroys the old clients on the next tick (V:`rest_api.py`:92,376–385,480–499). **Inferred—high:** Repeated failure after replacement implicates state shared across clients, but that includes rmw graph state, QoS/locator state and application execution, not just PDP. “One participant per process” is also not universal: contexts matter; the inspected application uses one default context.
- **Verified—recorded:** 7424 fits participant index 7 under the default domain-0 port formula. **Verified:** Fast DDS allocates IDs locally and mutates listening locators when ports cannot be opened; this is not server-assigned registration order. [RTPSDomain.cpp](https://github.com/eProsima/Fast-DDS/blob/v3.6.2/src/cpp/rtps/domain/RTPSDomain.cpp), [listening ports](https://fast-dds.docs.eprosima.com/en/latest/fastdds/transport/listening_locators.html). **Inferred—medium:** Late socket creation is plausible; latest successful server registration is unproved. Capture first DATA(p), server response and EDP times by full GUID. The delay cannot be attributed specifically to importing rclpy: database/auth context entry precedes `rclpy.init()` and node creation (V:`rest_api.py`:3402–3424). MySQL also restarts on full starts. The 2/2 temporal association is suggestive, not causal proof or evidence specifically for same-topic interest.
- **Verified:** Recovery is inferred from silence at a single throttled logging call site, not logged as a positive transition (V:`rest_api.py`:480–499; P:185–201). **Inferred—high:** The nominal upper bound is last negative log +60 s throttle +up to one 10 s timer period, **only if** the executor, timer and logging continue normally. Baseline 2's 20:57:27 upper bound is too tight; approximately 20:57:37 is defensible under that assumption. Baseline 3's 21:48:35–21:49:45 window already includes six seconds **before** the 21:48:41 probe. Neither window proves recovery followed the intervention. A blocked/dead spin thread, stopped timer, restart, or logging failure invalidates the bound altogether.

## 2. Fast DDS mechanics relevant to the failure

**Verified:** Client/server PDP uses reliable endpoints; EDPClient inherits EDPSimple and uses reliable, transient-local discovery endpoint proxies. The server puts relayed announcements into its writer histories and tracks pending acknowledgments. It is not a one-shot UDP broadcast with no retransmission machinery. [PDPClient.cpp:225–300](https://github.com/eProsima/Fast-DDS/blob/v3.6.2/src/cpp/rtps/builtin/discovery/participant/PDPClient.cpp#L225), [EDPSimple.cpp:769](https://github.com/eProsima/Fast-DDS/blob/v3.6.2/src/cpp/rtps/builtin/discovery/endpoint/EDPSimple.cpp#L769), [PDPServer.cpp:1252–1360](https://github.com/eProsima/Fast-DDS/blob/v3.6.2/src/cpp/rtps/builtin/discovery/participant/PDPServer.cpp#L1252).

**Inferred—high:** Separate three failure classes: information never reaches the reader; reliable history/sequence state prevents its delivery; information is delivered/acknowledged but endpoint processing fails. Normal HEARTBEAT/ACKNACK recovery addresses the first class, not necessarily the last. A server knowing an endpoint and a new reader learning it does not prove correct delivery or processing for an existing reader.

**Verified:** The server schedules PDP before its EDP send lists. The client EDP listener has an explicit unknown-participant rejection path, removing the discovery change from history around processing (writer path lines 114–133; reader analogue 260–279). [EDPSimpleListeners.cpp](https://github.com/eProsima/Fast-DDS/blob/v3.6.2/src/cpp/rtps/builtin/discovery/endpoint/EDPSimpleListeners.cpp#L114). **Inferred—medium:** H7 is mechanically possible, but sender order is not a cross-writer delivery guarantee. Prove whether bay DATA(p) was installed before its DATA(r/w), and whether the rejected change was acknowledged and ever republished. Seeing EDP in a pcap alone does not prove this race.

**Verified:** `DSClientEvent::event()` matches the connected server's EDP endpoints and keeps pinging while configured servers remain missing. Once connected, that event is not a periodic full graph rebuild. Server removal restarts the sync timer. Clients directly track server lease expiry; other clients' liveliness is mediated through server PDP. [DSClientEvent.cpp:55–101](https://github.com/eProsima/Fast-DDS/blob/v3.6.2/src/cpp/rtps/builtin/discovery/participant/timedevent/DSClientEvent.cpp#L55), [PDPClient.cpp:162–189,367–388](https://github.com/eProsima/Fast-DDS/blob/v3.6.2/src/cpp/rtps/builtin/discovery/participant/PDPClient.cpp#L162). **Inferred—high:** A healthy server lease need not repair a missing endpoint. A fresh client reconstructs local state; a server restart rebuilds server state only if clients reach it again. Neither requires already matched user endpoints to become unavailable immediately.

**Verified:** Disabling `fastdds.type_propagation` prevents creation of the local TypeLookupManager; the listener falls back when no manager exists. [BuiltinProtocols.cpp:142–151](https://github.com/eProsima/Fast-DDS/blob/v3.6.2/src/cpp/rtps/builtin/BuiltinProtocols.cpp#L142), [EDPSimpleListeners.cpp:140–155](https://github.com/eProsima/Fast-DDS/blob/v3.6.2/src/cpp/rtps/builtin/discovery/endpoint/EDPSimpleListeners.cpp#L140). **Inferred—high:** TypeLookup deadlock/lost-reply theories are substantially weakened for a REST participant actually using this profile. A mounted XML file is weaker evidence than effective participant properties. Disabling type propagation does not disable EDP or its reliability machinery.

**Verified:** S:`support.yaml` at `c9b6529` supplies neither profile config nor profile environment to the server; its command explicitly listens at the resolved server hostname. The ros2-docker Dockerfile at `4f7c26e6a7c71b8d435de17fabdfad83c24f782f`:154–170 has a socket-only health check and the direct server binary command. **Inferred—medium:** Missing profile is a configuration asymmetry, not proof of unwanted advertised addresses. Inspect actual server DATA(p), effective QoS and CLI override behavior before assuming E7 works as written. Its enabled type subsystem does not automatically imply type-resolution blocking in a disabled client.

**Inferred—medium:** UDP-only is a useful discriminator because central↔server are colocated containers: discovery can encounter SHM selection/namespace problems even though bay7 is remote. Private `/dev/shm`, identity collisions and inappropriate locators can matter. UDP counters cannot measure SHM. Removing SHM transport also does not necessarily disable the distinct DDS data-sharing delivery feature; record both separately.

## 4. Experiments ranked by information per garage minute

All actions below are **proposals**, not executed. **Inferred—high:** Keep image digests, profile hashes, versions and timestamps fixed; randomize A/B order and count all attempts, including failures to start. Do not call a five-run pass a permanent fix. Make comparisons off-garage first.

### A. Repair the observer, then capture one failure (highest priority)

**Inferred—high; cost:** one volley diagnostic build and one deployment, then no additional restart while observing.

Change V:`rest_api.py` near `refresh_bay_clients`: keep existing clients stable; log positive readiness transitions and an unthrottled 1 s diagnostic heartbeat with monotonic time, PID, per-service readiness and graph reader/writer GUIDs from **this node**, using the `no_mangle=True` queries in R:491–500. Log timer entry/exit and thread exceptions. Record fresh garage-info timestamps separately. For one diagnostic rmw build, log the four values at `rmw_service_server_is_available.cpp`:84,96,111,116 before early returns.

Readout: graph zero/unequal → graph/discovery processing; graph 1/1 but one match zero → endpoint matching; all four valid with false application status → handle/concurrency/application path. Missing heartbeat → execution failure, not recovery. Keep a C++ client created at startup as a non-actuating readiness control; no dispatcher start needed.

### B. Capture both sides before startup, with loss counters

**Inferred—high; cost:** piggyback A's single full restart; no image build if host capture tools suffice.

The existing `nsenter` capture after deploy can miss the initial burst. Start host captures **before** stack creation on central and bay7: `tcpdump -i any -s 0 -B 8192 -w startup-host.pcap 'udp or icmp'`; collect capture-drop statistics. After container namespace creation, add `nsenter -t "$PID" -n tcpdump -i any -s 0 -B 8192 -w startup-container.pcap 'udp or icmp'` on central/server/bay. These are proposed operator commands; administrative access may be needed.

Before/after snapshots in all three container namespaces and both hosts: `/proc/net/snmp`, `/proc/net/netstat`, `/proc/net/softnet_stat`, `ss -uamn`, interface counters, and host `tc -s qdisc`/`ethtool -S` where installed. Include `SndbufErrors`, `InErrors`, `NoPorts`, fragmentation/reassembly and capture losses, not only `RcvbufErrors`.

Readout: map full GUID → process → locators; trace bay PDP and both service EDP records, **server writer sequence numbers**, HEARTBEAT/ACKNACK/GAP/DATA_FRAG. Missing between captures → transport path; repeatedly requested but not resent → reliability/history; received and ACKed but absent locally → processing/cache. Distinguish actual DDS sends from packets merely visible on a host capture.

### C. Separate the “probe heals” interventions

**Inferred—high; cost:** no build, no restart beyond obtaining independent stuck runs; 1–2 min observation per intervention.
