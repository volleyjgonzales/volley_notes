01

Problem statement

The automated garage, the role of the scheduler, and the construction of a plan.

Domain

An automated parking garage

Vehicles are stored on trays. Every tray movement is performed by an AGV, which drives beneath the tray, lifts it, carries it and lowers it. The colours below are used consistently on every map in this deck.

AGV

Automated guided vehicle. A low-profile robot that lifts and transports one tray at a time. Named AGV-1, AGV-2, …

Tray

A legged platform that holds one vehicle or is empty. Named tray T15, tray T17, …; its front overdrive plate (ODP) is retractable.

Bay

The customer interface for vehicle drop-off and pick-up, for example bay B21. Operates in insert and retrieve modes.

Stalls and waypoints

Parking stalls (stall P17) store trays; waypoints (waypoint W22) are aisle positions traversed by AGVs.

Chargers (VECS)

Volley EV charging stations, which charge AGVs and vehicles parked on trays.

Lifts (VRC)

Vertical reciprocating conveyors, which transport an AGV, with or without a tray, between floors.

When a customer requests a vehicle, the system must deliver the tray holding that vehicle to a bay. AGVs are the only actuated agents. Trays are passive obstacles: a tray in the path must be relocated first. Bays, chargers and lifts are resources with their own states and durations.

System context

Dispatch requests, the scheduler plans, the fleet executes

Dispatch (the central package) owns the job queue and the executing schedule, and may call the planner every 850 ms. At present it calls the planner only when no job is active, so every plan starts from an idle fleet; Part 4 returns to this. The scheduler maps a garage snapshot and a set of jobs to an action graph; it does not communicate with the robots.

Stage 5 returns an action DAG: no times, only the order Dispatch must respect
The event DAG is the central data structure: a graph of planned events (tray moves, AGV moves, bay transitions) with must-happen-before edges. Each task-planning stage reads it and modifies it in place. This in-place modification is the principal source of the coupling the refactor addresses. Step 2 introduces one small retrieve on the map. Steps 3 to 6 follow it: the event DAG read as a motion problem; the routes in space; the timed motions; and the action DAG. In short: the event DAG (order, no times) read as a motion problem; the timed motions CHUGG returns (AGV-2 waits at W18 for AGV-1); and the action DAG, where that wait becomes one edge, "W22 free". Times are illustrative steps, not seconds.
Inputs and outputs

From a job to an ordered graph of actions

Input: goals. A job states an outcome, such as "the vehicle on tray T17 is handed over at bay B21", not the moves. The planner chooses the bay, trays, AGVs and routes.

Output: a partial order. Each action names one machine and the actions that must complete before it. No times are given; the order alone keeps execution safe.

Simplified to one job and no other trays; subsequent slides introduce them.

Each lane is a machine; each arrow means "must complete before". The two cross-lane dependencies (in the accent colour) are what make the plan safe without a clock: the tray enters the bay only once the bay is in retrieve mode, and the hand-over happens only once the tray is lowered. Dispatch releases each action as soon as its predecessors have completed.

Task planning · stage 2

Tray assignment: which empty tray goes into the bay?

  • The job requests an empty tray, not a specific one. The choice belongs to tray assignment and affects the plan: some choices require other trays to be moved first.
  • Current rule: search outward from the bay, with cost = travel time + 30 s per obstructing tray, and select the lowest cost.
  • Other rules are possible, for example keeping the stalls nearest the bay for vehicles. The rule currently resides in the 560-line DoTrayAssignments; behind an interface, alternative rules can be compared on the benchmark set.
Costs are illustrative. The real search ignores trays and AGVs as obstacles but charges 30 s for each tray it crosses, so a buried empty tray can still be chosen; the main loop then plans the moves that clear its way. The same stage also gives destinations to trays that must leave (the empty tray in a bay before a retrieve) and adds moves for trays that block a route.

Task planning · stage 3

AGV assignment: which AGV moves each tray

  • A cost for each pair of AGV and tray move: the time to reach and lift the tray.
  • A bottleneck matching minimises the largest chosen cost, not the total.
  • Both the cost and the matching rule are policies. Both currently reside in the 365-line DoAgvAssignments, which the second interface of the ticket replaces.
The values are illustrative. The real implementation iterates over the tray moves that can start next and repeats until every tray move has an AGV. Whether minimising the worst case is the right objective is a question for the benchmark set.

Motion planning · stage 4

CHUGG converts the event DAG into timed, collision-free paths

Input

The event DAG with an AGV for every move, the garage graph, and the collision table (which positions overlap).

Output

A timed trajectory for every AGV: where each one is at every moment, with no two in conflict.

Method

Events are planned one at a time, in DAG order. Each new path avoids the paths already planned, which never change.

Example: AGV-1's event is planned first; AGV-2 must wait at vertex 6 until vertex 3 is free. The order of events therefore determines which AGV waits. Motion planning is outside the scope of this ticket.

CHUGG (Constrained Huge Unknown Graph alGorithm) receives a multi-agent path-finding problem with precedence constraints. Its method is prioritized planning, with a single-agent search (SIPP, safe-interval path planning) for each event. It is fast, but an earlier event never yields to a later one, so the event order produced by task planning shapes the result.

Action graph · stage 5

Action graph: an execution order robust to timing variation

Objective. Dispatch must execute the plan safely when actual action durations differ from the planned ones.

Issue. A timetable fixes when each action starts. A late AGV-1 is still in cell B when AGV-2 enters on schedule (figure, middle).

Solution. Stage 5 converts the timed paths into an action graph: one box per action, one arrow per "must complete before", added between AGVs wherever both use the same cell. AGV-2 waits for the arrow, not for a clock time (figure, bottom).

The scheduler returns this graph to Dispatch, which releases each action as soon as its predecessors have completed. It is built from the timed paths by keeping, for each cell, the order in which AGVs pass through it, and each AGV's own sequence of actions. The example is the five-cell map of the figure.

Jira · Scheduler Core Refactor

Objective and scope

Objective. Move tray-move planning and AGV assignment out of large Scheduler methods and behind generic, replaceable interfaces. Default implementations must reproduce current behaviour.

Definition of Done

  • Two generic interfaces: tray assignment and AGV assignment
  • Two behaviour-equivalent default implementations
  • 10+ real-site benchmark scenarios per solver, with saved baselines
  • Every assignment call site routed through the interfaces; old paths removed

Out of scope: changes to CHUGG/SIPP motion planning, a new optimal solver, adding to active schedules.

SW2-769 Done

Scheduler package reorganization.

SW2-484 In progress

Tray solver interface. The first implementation ticket.

SW2-487 To do

The scope is deliberately narrow: no new algorithm and no change to motion planning. It is an enabling refactor. Its value is that future tray or AGV solvers can be introduced behind an interface and evaluated quantitatively.

Issues

Structural limitations of the planning core

Implicit inputs and outputs

The assignment methods read and modify the event DAG, the working garage state and member maps in place. Their signatures do not state what they require or change.

No isolated testing

Testing tray assignment requires constructing a complete Scheduler. There is no separable unit and no point of substitution.

Shared helpers

The same helpers (headings, blockers, empty-tray selection) are used by job expansion. Relocating them without redesign either breaks callers or introduces back-references.

Inconsistent error handling

BoolStringPair, std::optional and silent false returns are mixed; some failures lose their cause.

Inconsistent naming

Names such as gg_, table_, CollisionEntityId and "disabled" obscure their meaning and impede comprehension.

No performance baseline

Without a benchmark set, the effect of a change on plan quality or planning time cannot be determined.

The first three are addressed directly by the interfaces. The last three make the work safe and reviewable: a single error type, descriptive names, and measurable baselines.

03

Proposed changes

Interfaces, module layout, naming and error handling, delivered in incremental steps that preserve behaviour.

Principles

Guiding principles

1 · Behavioural parity

The default solvers reproduce current behaviour exactly: identical assignments, identical event DAG after reduction, and byte-identical responses on the baseline fixtures. Improvements follow separately, behind the interfaces.

2 · Incremental, mechanical steps

Each pull request contains one kind of change (move, rename or extract) and is verified by parity tests rather than by manual review of large diffs.

3 · Limited renaming scope

Renames are confined to scheduler and planner_core. common_ros is used by many other modules; its names are translated at the package boundary instead.

4 · Folders first, packages when justified

Stage folders, each with its own build target, within scheduler. A stage becomes a separate package only once it has a second consumer and a stable API.

Principle 1 is the most important, as it makes a large refactor reviewable. Any step that changes a plan is, by definition, defective.
Architecture · current

Scheduler today: one class, six responsibilities

Method counts from scheduler.hpp; the grouping into responsibilities is this review's. Accent: the two responsibilities this ticket extracts.

The class is cohesive in data, not in purpose: every method can reach the layout, the graphs, the collision table and the shared context, so every method can call every other. That is what makes the assignment stages hard to test or replace on their own. The good news for the refactor is that per-call state is already separated from the long-lived members: Plan() is const and builds a fresh context each call.
Target architecture

Plan() as an orchestrator of replaceable stages

delivered by this ticket    enabled for later

The orchestrator defines the order of the stages and owns the solver objects. Each assignment stage exposes a minimal interface with a single entry point. Shared services that are currently Scheduler members (gg_, table_) become an explicit GarageServices object passed as an argument.
Architecture · proposed

Scheduler after the refactor: a thin orchestrator

class Scheduler {                     // sketch
 public:
  Scheduler(GarageServices services, SolverSet solvers);
  PlanResponse Plan(const PlanRequest& req) const;
 private:
  GarageServices services_;   // layout, graphs, cost model
  std::unique_ptr<tray_assignment::Solver> tray_solver_;
  std::unique_ptr<agv_assignment::Solver>  agv_solver_;
  SchedulerConfig config_;    // bay readiness ratio, audit
};

PlanResponse Scheduler::Plan(const PlanRequest& req) const {
  PlanContext ctx = MakePlanContext(req, services_);
  ExpandJobs(ctx, req.pending_jobs);         // job_expansion/
  auto trays = tray_solver_->Solve({ctx.initial_state, ctx.event_dag});
  if(!trays) return FailAll(ctx, trays.error());
  ApplyTrayAssignment(ctx, *trays);
  if(auto r = agv_solver_->SolveInPlace(
         {ctx.initial_state, ctx.first_event_by_tray}, ctx.event_dag); !r)
    return FailAll(ctx, r.error());
  auto motions = PlanMotions(ctx, services_); // motion_planning/
  return BuildResponse(ctx, BuildActionDag(ctx, motions));
}

One responsibility left

The class sequences the stages and owns the solver objects. The stage logic moves to stage folders; the 55 methods become a handful.

Dependencies passed in

Services and solvers arrive through the constructor. A test builds a Scheduler with a fake or candidate solver, or calls a solver with no Scheduler at all.

Lifetimes made explicit

Immutable site services, runtime configuration and per-call PlanContext become three separate types instead of members and a shared pointer.

SolverSet is a small struct of the two solver pointers; the default set holds the DefaultSolvers that reproduce today's behaviour. The code is a sketch: names follow the proposal, error handling uses stdx::Expected, and the stages run in the same order as today. Motion planning and the action graph keep their current functions; their interfaces are Part 4.
Tray assignment interface

Read-only input, returned result, single point of application

namespace volley::task_planning::tray_assignment {
struct Input {          // read-only view
  const DiscreteGarageState& initial_state;
  const EventDag& event_dag;
};
struct Result {         // an edit log
  std::vector<TrayFill> fills;   // blanks filled
  std::vector<DagEdit>  edits;   // events, edges
  // + first event per tray, for AGV assignment
};
class Solver {
 public:
  virtual ~Solver() = default;
  [[nodiscard]] virtual stdx::Expected<Result>
  Solve(const Input& input) const = 0;
};
}  // namespace
// the only writer of the plan context
ApplyTrayAssignment(plan_ctx, result);

No side effects in Solve

The solver receives a const view and returns its decisions. Two solvers can be run on the same input and compared.

Inspectable results

Assignments and edits are plain data: tests assert on them directly, and logs record exactly what a solver changed.

Ordered replay preserves parity

ApplyTrayAssignment applies the edits in the order the current code makes them, so the resulting event DAG is identical.

TrayFill: one blank (tray or destination) filled on an existing tray move. The study site explains each name and the alternatives considered.

This is the central design decision. Returning a result rather than modifying shared state is what makes the solver testable and replaceable. The edit log is ordered so that the current DAG is reproduced exactly.

No Result struct in the first version

The AGV loop reads the graph it builds: matched moves, AGVs already assigned, and edges added for path repair. Returning an edit log would require replicating that state inside the solver, a parity risk before benchmarks exist.

Path forward

With parity tests and benchmarks in place, the solver works on a private copy of the event DAG and returns AgvFill entries and an ordered edit log, applied by ApplyAgvAssignment.

Shared with tray assignment now

Folder, build target, stdx errors, GarageServices and pure, separately testable cost functions.

The mutable argument is explicit in the signature, so a reader sees which stage edits the plan. Everything that can be pure already is: the cost estimates and the feasibility checks. The study site lists every name and the reasons for it.

Each stage moves out of scheduler.cpp into its own folder; what remains is Plan(), which calls the stages in order.

Enforced boundaries

Each stage is a separate library target. A CI include check prevents a stage from using another stage's private headers.

Separate packages deferred

Packages add release and ownership overhead before the APIs are stable. A folder can be promoted later at low cost; action_graph is the first candidate.

Architecture · dependency rules

Dependencies point one way

Rules

A layer may use the layers below it, never above. Stages meet only through core/ types and the orchestrator. ROS messages stop at ros/.

Enforced, not documented

One CMake library target per stage, linking only core; a CI check rejects an include of another stage's private headers.

What it buys

A stage can be built, tested and later promoted to its own package without untangling the others.

This is a layered (ports-and-adapters style) arrangement: ros/ is the adapter to the outside world, the stages are the domain logic, core/ holds what they share. The current code has no such boundaries: everything is one target and one translation unit. Stages may call the external libraries directly (the tray solver uses the motion_planner searches), which is allowed because those sit at the bottom.

Future · the event graph

A staged path to improved plans

1 Record the kind of each edge

Causal, path-dependent, resource-order or conservative, together with the rule that created it. Behaviour is unchanged, and the change fits the new interfaces.

2 Quantify the cost of over-constraint

On the benchmark set, compare makespan and retrieve arrival times with all edges against causal edges only. If the difference is small, no further change is needed.

3 Delegate the free orderings to the solver

Pass resource-order edges as choices to Priority-Based Search with Precedence Constraints (PBS-PC); causal edges remain hard constraints.

4 Introduce an explicit objective

Begin with bay selection and job ordering, evaluated by predicted retrieve waiting time, behind the new solver interfaces.

Questions to resolve before step 3: the primary objective (retrieve waiting time, throughput or a weighted combination), the permitted duration of a planning call, and whether bay and patron action durations can be bounded.
Future · motion planning

A solver interface for motion planning

This is more involved than the task-planning interfaces, because CHUGG's inputs are tied to event vertex indices and the collision table. A MotionProblem / MotionPlan pair would allow other planners (conflict-based search, PBS) to be evaluated, including planners that support only part of the problem.
Future · performance

Measuring planning time: an initial proposal

1 · Stage timers and counters

A per-call record of each stage's duration, with the work behind it: searches run, nodes expanded, blocking trays resolved. Always on, and stored in every simulation recording.

2 · Profiling on demand

A sampling profiler on the replay tests for call-level detail, without code changes; an instrumenting profiler where finer timelines are needed.

3 · Fleet monitoring later

OpenTelemetry and Grafana once planning time must be followed across sites. One scope macro in the code keeps the backend replaceable.

Evaluation. An agreed time budget per call; growth measured against each size parameter (jobs, trays, AGVs, graph size, blockers); a catalogue of stress cases; slow plans in the field saved as replayable fixtures; runtime and work-counter gates in CI, with plan quality measured separately.

Known candidates for steep growth: the tray-search step checks every tray, the blocking-tray loop searches again per blocker, every job method replays the event DAG, HideAgvs backtracks, and CHUGG's heuristic table is cubic in the number of poses. The study site lists them under Future work.
