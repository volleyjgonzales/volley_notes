What problem does this software solve?

A customer vehicle sits on a tray inside an automated parking facility. An AGV (automated guided vehicle) drives under a tray, raises its lift, and carries the tray. A bay is the customer-facing handoff room; a waypoint is a navigation node; a parking node is where trays are stored; an AGV charge node is where robots recharge. Some installations have a VECS (EV charging station under a parking node) or a VRC (vertical reciprocating conveyor, a lift between floors). These are different resources with different rules.

A job such as retrieve this payload does not say how to do it. The Scheduler decides which tray moves are needed, which AGV does each one, which operations must happen first, and how long everything takes. It then returns a schedule of discrete commands that Dispatch executes. The scheduler never drives a motor and never talks to an AGV directly.

The key distinction is what should happen versus how and when it happens:

Layer Question Example Where it lives
Job What outcome is requested? Retrieve a payload SchedulerJob.msg
Event What discrete state change is needed? Move tray 17 into bay 21 ScheduleEvent subclasses, ctx->events
Motion How does an AGV get there over time? Timed pose changes along graph edges ContinuousState from CHUGG
Action What command is sent to which machine? TYPE_AGV_COMMAND from node 13 to node 15 ActionNode.msg inside Schedule.msg

Where the scheduler runs: the node and its interfaces

The package builds one shared library (libscheduler: scheduler.cpp, utils.cpp) and one ROS 2 component (scheduler_component.cpp, scheduler_ros.cpp) that is also installed as the executable scheduler_node. Three layers wrap each other:

  1. SchedulerComponent reads ROS parameters (layout, scheduler.cost_audit, scheduler.bay_readiness_ratio, and the AGV / VRC / bay / VECS performance limits in ReadParams), finds the layout file with GetLayoutPathByName, and builds a SchedulerRos. Missing parameters exit the process.
  2. SchedulerRos owns every ROS object: the plan service, the set_bay_readiness_ratio service, the debug/printdags toggle, two 5 s publishers, and four clients into /central. It owns the Scheduler through a shared_ptr.
  3. Scheduler is the planning core. Apart from a logger and rclcpp::Time, it knows nothing about ROS transport, which is why tests can construct it directly.

The whole service handler is a few lines. This is the only place where ROS hands a request to the planner:

// Where: SchedulerRos::SchedulerRos(...) in src/scheduler_ros.cpp, the "plan" service callback.
//   this        -> SchedulerRos (the ROS adapter, not the planner)
//   scheduler_  -> std::shared_ptr<volley::Scheduler>, created in this constructor
//   request     -> PlanSrv::Request::SharedPtr; request->request_data is a PlanRequestMsg
plan_srv_ = rclcppx::CreateService<PlanSrv>(node_, "plan",
    [this](PlanSrv::Request::SharedPtr request, PlanSrv::Response::SharedPtr response) {
      PlanResponseMsg response_msg = scheduler_->Plan(request->request_data, node_->now());
      rclcpp::Time now = node_->now();
      for(auto& job_data : response_msg.scheduled_jobs) {
        job_data.job.time_planned = now;          // stamp every job, failed or not
      }
      response->response_data = std::move(response_msg);
      return response;
    }, 1u);

Two side channels matter when you debug: set_bay_readiness_ratio stores a new ratio in the std::atomic<float> bay_readiness_ratio_ and, if it changed, asks /central/rebalance_garage for a REBALANCE_GARAGE job; and a failed INSERT job triggers /central/clean_garage from inside Plan().

The physical garage and its coordinate system

The supplied Pecos layout has 28 nodes and 37 undirected edges in two YAML sections (sandbox_eng and sandbox_qa). It defines two bays (B7, B21), three AGV charging nodes (C10, C14, C16), plus parking and waypoint nodes. It does not define a VRC. Node positions come from the YAML; connectivity comes from the edges list, not from visual distance.

Notice how dense the parking block is: stalls touch along x, so a tray at P17 can only leave through P15 or P20. That is why blocking trays (section 16) are a core problem rather than an edge case.

Geometric versus logical position

The continuous position vector \mathbf p=[x,y]^\mathsf T\in\mathbb R^2 holds the horizontal coordinate x and vertical coordinate y, both in metres. A planar configuration \mathbf q=[x,y,\theta]^\mathsf T\in\mathbb R^3 adds the heading \theta. In GeometricPose.msg the yaw \theta is in radians. GaragePose.msg is different: it holds a node identifier i\in\mathbb N and an integer heading h\in\mathbb Z in degrees. The planner works almost entirely in GaragePose.

# msg/GeometricPose.msg          # msg/GaragePose.msg
float32 x       # metres        uint32 node_id
float32 y       # metres        int16 heading   # degrees, +CCW from local north; 90 = west
float32 yaw     # radians

Layout, GarageGraph and CollisionTable: three views of the same garage

The scheduler builds three static objects from the layout file, once, in its constructor, and uses them for every plan:

// src/scheduler.cpp — Scheduler::Scheduler(std::string layout_filepath, rclcpp::Logger logger,
//                                          const SchedulerParams& params)
layout_(std::make_shared<Layout>(layout_filepath)),   // LayoutSPtr: the parsed YAML
pg_(layout_),                                         // volley::PoseGraph, built from the Layout
gg_(pg_),                                             // volley::GarageGraph, the search graph
table_(gg_, logger),                                  // volley::CollisionTable, built from the graph
// ...then InitRetrievalHeadings() stores one retrieval heading per parking node in gg_

They are easy to confuse because all three "describe the garage". The difference is the question each one answers.

  • Layout (layout_) is about places. It is the YAML file in memory: nodes with an id, a type, a position in metres, the headings they allow and whether an AGV may rotate there; undirected edges between node ids; parking-window sizes; bay facts (inbound heading, prioritisation, floors). You ask it "what is node 22?" with layout_->GetNodeById(22), which returns std::optional<GarageNodeMsg>.
  • GarageGraph (gg_) is about motion. Its vertices are poses, a node plus a heading, and its edges are the moves between poses. Every heading a node lists in the YAML gives two poses, the heading and its reciprocal, so most nodes are two vertices and W22, which lists headings 0 and 90, is four; a heading the node does not allow has no vertex at all. Every path search runs on gg_. You translate between the two worlds with gg_.GetVertexFromPose(GaragePoseMsg) -> std::optional<Vertex> and back with gg_.GetPoseFromVertex(v) or gg_.GarageNodeFromVertex(v).
  • CollisionTable (table_) is about space. It answers one question: would footprint A at pose a overlap footprint B at pose b? The scheduler's direct calls use table_.Query(fixed_id, queried_id, fixed_pose, queried_pose) -> bool; other overloads take edges (moves), or return every conflicting pose and edge at once. The footprint is picked by a collision id (CollisionEntityId_t), computed from the entity's state by CollisionEntityIdFromAgvState, ...FromTrayState or ...FromPayloadState, so an empty AGV, an AGV carrying a tray and a tray with a large car get the right shapes. Because it depends on poses, not just nodes, the same two nodes can conflict at one heading and be fine at another.

Most code does not call Query directly. It asks volley::GetStaticFilter(id, gg_, working_state, table_, ...), which uses the table to mark which graph vertices a given entity cannot use given everything in working_state, and then tests filters.IsEnabled(vertex). ctx->disabledness_filters, built once per Plan(), works the same way for disabled nodes and entities. The direct Query calls are in DoTrayAssignments (is another tray in the way of the root tray's next pose?) and AgvMatchingEventDeps (would two AGVs conflict?).

The fourth structure is the one that changes: DiscreteGarageState (section 5) records who is where right now. Layout, graph and table never change after start-up; the state is different in every plan request. Section 6 opens up the first three: their containers, their lookups and what each costs.

A request is not a plan

PlanRequest                                   PlanResponse
  ├── id: Guid                                  ├── success: bool, message: string, id: Guid

Only pending_jobs are planned. base_schedule is the immutable part of a schedule that is already executing: Plan() marks every AGV, node, bay and VECS used by it as disabled in the initial state, so the new plan cannot reuse them.

DiscreteGarageState: the bridge between the garage and the planner

DiscreteGarageState is the most important type in the system. The Scheduler never plans over geometry directly; it plans over this structured snapshot of AGVs, trays, bays, payloads, VECS, VRCs and disabled nodes. The ROS message carries them as arrays; inside the class they are std::maps keyed by id (agvs_, trays_, bays_, vexen_, vrcs_; payloads_ by GUID) plus a std::set of disabled node ids. Ordered maps are deliberate: the state's hash depends on iteration order. Every physical fact the planner cares about must be expressible in it.

How it is used in the scheduler:

  • Built once per call by ValidateBaseState(request_data.base_state, *layout_) in utils.cpp. It rejects duplicate entities, payloads that fit no resource window, and AGVs or trays on poses that do not exist in the layout. It does not check that entities overlap.
  • Copied freely. It is a value type. working_state = ctx->initial_state makes an independent copy that a function can mutate without affecting anyone else.
  • Advanced by events. event->Apply(working_state) returns a BoolStringPair and moves entities discretely (a tray simply appears at its destination).
  • Queried constantly with GetAgv(id), GetTray(id), GetTrayOnNode(node), GetPayload(guid), GetBay(id), GetVecs(vecs_id) (a VECS id is its node id), each returning std::optional. Each is a std::map lookup, O(\log n); GetTrayOnNode scans the trays.
  • Not quite atomic. The header promises that a failed event leaves the state unchanged. OnEvent(AgvPoseChangedMsg) breaks that: it moves the carried tray before checking whether another AGV is on the destination node, so a failed AGV move can leave the tray moved (common_ros/src/discrete_garage_state.cpp:1141–:1165). Replays that ignore a failure would see a tray where its AGV is not.

PoseGraph: from nodes to poses

A YAML node lists headings in 0–179. PoseGraph turns each one into two poses, the heading and its reciprocal, because a centred rectangular footprint covers the same area either way:

// common_ros/src/pose_utils.cpp
std::vector<int16_t> GetAllowedHeadings(const GarageNodeMsg& node) {
  std::vector<int16_t> headings;
  for(uint16_t heading : node.headings) {           // YAML headings, 0..179
    headings.emplace_back(volley::Wrap(heading));
    headings.emplace_back(volley::Wrap(heading + 180));
  }
  std::sort(headings.begin(), headings.end());
  return headings;
}

So a node with one YAML heading (most Pecos nodes list [90]) has two poses, −90 and 90, and W22, which lists [0, 90], has four: −90, 0, 90 and 180. Pecos's 28 nodes give 60 poses. GaragePose.msg fixes the range: a heading is an int16 in [-179, 180], so Wrap(90 + 180) is −90, not 270 (a scheduler test expects ConstructGaragePose(1, -90)). Because the list is sorted, −90 comes first at each node.

PoseGraph stores the poses in three containers:

  • poses_, a std::vector<GaragePoseMsg> ordered by node id, then heading. A pose's pose index is its position here.
  • pose_indices_, a std::map<GaragePoseMsg, int, GaragePoseComparator> from pose to index (GetPoseIndex returns kInvalidIndex, −1, when it is missing).
  • pose_neighbors_, a flat std::vector<int> with eight slots per pose, one per PoseNeighbor: FORWARD, RIGHT, BACK, LEFT, ROT_RIGHT, ROT_LEFT, VRC_UP, VRC_DOWN. Slot k of pose i is at 8 * i + k and holds the neighbour's pose index, or −1. (The header comment still says "six"; the VRC slots were added later.)
  • overlapping_sized_poses_, per pose and resource size, the smallest conflicting sized poses.

The neighbour slots are filled by three rules:

  1. Translations. For each Layout neighbour of the node, the destination must allow the same heading, and the edge must not have a disallowed orientation equal to that heading or its reciprocal. The slot is chosen from the bearing to the neighbour relative to the heading, within 0.1 rad (about 5.7°) of 0°, ±90° or 180°. Any other angle throws "invalid translation connection" when the scheduler starts.
  2. Rotations, only where rotation_allowed is true: the nearest other heading clockwise and counter-clockwise. With only h and h+180 both slots point at the same pose.
  3. VRC moves: nodes of the same VRC on adjacent floors, classified by floor (up or down), not by bearing.

GarageGraph and its Vertex

The GarageGraph constructor walks pg.GetPoses() in order and calls boost::add_vertex(pose, base_graph_) for each, recording pose_to_vertex_[pose] = vert. A second loop adds one directed edge for every neighbour slot that is not −1. AddEdge gives each edge a Transition:

  • a rotation, with its length in radians;
  • a VRC transition, with its length the floor-to-floor height;
  • otherwise LOCOMOTE or STRAFE, depending on whether the motion is mostly along or across the heading, with its length in metres.

Reading the boost::adjacency_list type

boost::adjacency_list is a class template from the Boost Graph Library (BGL) with seven template parameters. BoostPoseGraph passes the first five and takes Boost's defaults for the last two. The names in the first column are Boost's own; they are worth learning because Boost's documentation and error messages use them.

# Parameter (Boost's name) BoostPoseGraph passes What it decides
1 OutEdgeList boost::vecS The container for each vertex's list of out-edges: a std::vector.
2 VertexList boost::vecS The container for the vertices: a std::vector. This choice is what makes vertex_descriptor, and so Vertex, a std::size_t index. With listS it would be an opaque pointer instead.
3 Directed boost::bidirectionalS Edges are one-way, and each vertex keeps an in-edge list as well as an out-edge list, so in_edges and in_degree are cheap. directedS would keep only out-edges; undirectedS would make every edge two-way.
4 VertexProperties GaragePoseMsg The data stored with each vertex (Boost calls it the bundled vertex property), read with base_graph_[v]. It is the vertex's payload, not the vertex.
5 EdgeProperties boost::property<boost::edge_index_t, std::size_t, Transition> The data stored with each edge: an edge index and a Transition. Explained below.
6 GraphProperties not passed: boost::no_property Data stored once for the whole graph: none.
7 EdgeList not passed: boost::listS The container for the graph-wide edge list: a std::list. In a bidirectional graph each edge, with its properties, is stored here once; a vertex's out- and in-edge lists hold iterators into it.

Why the vertex is not a GaragePoseMsg. The fourth argument is not the vertex type. Boost calls it VertexProperties: the data stored with each vertex. The graph names its vertices with a separate type, vertex_descriptor, which Boost derives from parameter 2. With VertexList = boost::vecS it is a std::size_t, and the valid vertices are exactly the contiguous range [0, \text{num\_vertices}(g)). So a vertex and its pose are two different things:

using Vertex = BoostPoseGraph::vertex_descriptor;   // std::size_t
Vertex v = 44;                                       // a descriptor: just a number, not a pose
GaragePoseMsg& pose = base_graph_[v];               // the payload stored with it: {node_id: 22, heading: 90}

This is how BGL works for every graph, not a Volley choice. It has five practical consequences:

  1. Algorithms work on descriptors. breadth_first_search, dijkstra_shortest_paths and topological_sort take descriptors, not application payloads. They keep their working data (distance, predecessor, colour) per vertex, and with vecS a descriptor can index a plain vector directly: dist[v]. MakeVertexVectorPropertyMap<T>() builds such a vector.
  2. Finding a vertex from its payload needs a separate lookup. BGL builds no index from a GaragePoseMsg to a descriptor. GarageGraph therefore keeps pose_to_vertex_, a std::unordered_map from pose to vertex.
  3. Descriptors are cheap, but they are stable only while no vertex is removed. A descriptor is 8 bytes on a 64-bit build. With vecS, removing a vertex renumbers every later vertex, which invalidates stored descriptors and any table built from them (pose_to_vertex_ included). GarageGraph never removes a vertex after construction, so its descriptors are safe to keep. ScheduleEventDag does remove vertices, and the same renumbering applies there (section 12.4).
  4. The payload type and the graph shape are independent. DagBase<T> uses adjacency_list<vecS, vecS, bidirectionalS, std::shared_ptr<T>>. Its vertices are also std::size_t descriptors, and the payload is the event pointer (section 12.3).
  5. Edges have their own identity and their own properties. An edge is named by an edge_descriptor (the Edge alias). GarageGraph stores two things with each edge: a tagged edge index and a Transition payload. Unlike vertex numbers, edge indices are not assigned by BGL; the application has to maintain them, and AddEdge does.

The edge argument. The fifth parameter is the data stored with each edge. BGL has two ways to write it, and BoostPoseGraph combines them:

  • Bundled properties (the current Boost documentation's recommended style). An ordinary struct holds the edge's data, and you read it with member access: g[e].index, g[e].transition. BGL can also build a property map from a pointer to a member, get(&EdgeProperties::index, g), so algorithms read bundled data directly. Bundled properties are not new: they have been in BGL for about two decades.
  • Tagged (interior) properties, the older style. boost::property<Tag, T, Base> stores a value of type T under a tag. Here Tag = boost::edge_index_t (a tag Boost predefines to mean "edge index"), T = std::size_t, and Base = Transition. When the last link of the chain is a plain struct rather than another property<...>, Boost treats it as the bundled payload. So get(boost::edge_index, g) reads the index, and g[e] returns the Transition&.

In memory each edge carries roughly {m_value: std::size_t, m_base: Transition}, and the two parts are read in two different ways:

// common_ros/src/garage_graph.cpp, GarageGraph::AddEdge (abridged)
size_t next_edge_index = boost::num_edges(base_graph_);   // edges are numbered 0, 1, 2, ... as they are added
std::tie(e, added) = boost::add_edge(pose_to_vertex_[src], pose_to_vertex_[dst],
                                     {next_edge_index, transition},    // {m_value, m_base}
                                     base_graph_);
boost::put(edge_index_, e, next_edge_index);              // writes the same index again

// reading an edge e
std::size_t i = edge_index_[e];           // the tagged part: edge_index_ = boost::get(boost::edge_index, base_graph_)
Transition& t = base_graph_[e];          // the bundled part; for edge 44 -> 59: {type: LOCOMOTE, length: 2.857}

Why an edge index at all. An edge_descriptor is a small struct, {m_source, m_target, m_eproperty}: the two vertex numbers and a pointer to the edge's stored properties. That is enough to read the edge, but it cannot index a vector. AddEdge therefore stores num_edges() at insertion time as the edge's index, so edges are numbered 0 to E-1 in the order they were added. MakeEdgeVectorPropertyMap<T>() and edge_index_to_vertices_ use that number to keep per-edge data in plain vectors, the same pattern as for vertices.

The modern equivalent, and why it is not a drop-in change here. Written in the bundled style, the same graph is:

// the bundled-property style (not what common_ros does today)
struct TransitionEdge {
  std::size_t index;       // maintained by AddEdge, exactly as now
  Transition transition;
};
using BoostPoseGraph = boost::adjacency_list<boost::vecS, boost::vecS, boost::bidirectionalS,
                                             GaragePoseMsg, TransitionEdge>;

auto [e, added] = boost::add_edge(u, v, TransitionEdge{.index = next_edge_index, .transition = t}, g);
std::size_t i = g[e].index;                              // or get(&TransitionEdge::index, g)[e]
const Transition& tr = g[e].transition;
auto index_map = get(&TransitionEdge::index, g);         // a property map from a member pointer
boost::vector_property_map<double, decltype(index_map)> per_edge(boost::num_edges(g), index_map);

The two styles look up the index through different mechanisms: get(boost::edge_index, g) only exists with the tagged property. GarageGraph exposes the tagged form in its public API: EdgeVectorPropertyMap<T> is defined as a vector_property_map over property_map<BoostPoseGraph, boost::edge_index_t>::type, and MakeEdgeVectorPropertyMap<T>() returns it. Switching to the bundled struct therefore changes a public common_ros type, and every caller outside the snapshots (the motion planner, for example) has to be checked. It also changes base_graph_[e] from a Transition& to the struct, so readers would write base_graph_[e].transition. It is a sensible cleanup, but one for common_ros; doc 04 lists it (section 6.1).

What a vertex actually is:

  • A number. With vecS as the vertex container, a Boost vertex_descriptor is a std::size_t index into the graph's internal vector of vertices. A Vertex is valid when it is less than NumVertices(); that is all HasVertex checks.
  • What is stored at that index: one entry of Boost's vertex vector (m_vertices[v], Figure 12) with three members:
    • the bundled GaragePoseMsg, read with base_graph_[v] (template parameter 4);
    • the out-edge list, a std::vector (parameter 1);
    • the in-edge list, present because the graph is bidirectionalS (parameter 3).
    The edge lists hold the target vertex and an iterator into the graph-wide edge list; each edge's index and Transition are stored there once, not in the vertex. Nothing else is stored: there is no node type, no position and no occupancy at a vertex. Node facts come from the Layout (GarageNodeFromVertex looks the node up and copies it), and occupancy comes from DiscreteGarageState.
  • The numbering is the PoseGraph order: vertex i is pose index i, that is, node id ascending, then heading ascending. On Pecos, W22's poses {node_id: 22, heading: -90}, {node_id: 22, heading: 0}, {node_id: 22, heading: 90} and {node_id: 22, heading: 180} are vertices 42, 43, 44 and 45.
  • Numbers are stable. Nothing adds or removes vertices after construction, so a Vertex stays valid for the scheduler's lifetime. Compare ScheduleEventDag, where Remove renumbers later vertices (section 12.4). A Vertex means nothing outside one layout: never store one, or compare one across layouts or builds.
  • Per-vertex data lives outside the graph. MakeVertexVectorPropertyMap<T>() returns a vector indexed by Vertex, and MakeEdgeVectorPropertyMap<T>() a vector indexed by edge index. That is the pattern for anything a search needs per vertex or per edge. GraphFilterProperties::IsEnabled(vertex) and IsEnabled(edge) are in motion_planner, which is not in the snapshots, so how they store their flags is not confirmed.

When GetVertexFromPose returns nothing

A pose is a vertex of gg_ only if the node allows that heading, and the lookup is an exact hash match on (node_id, heading): nothing normalises the heading first. An empty optional therefore means one of three things:

  • the node id is not in the layout;
  • the heading is not one of the node's YAML headings or their reciprocals;
  • the heading is outside [-179, 180], so it does not match the stored value (for example 270 instead of the stored −90).

Any of these produces the "does not exist in garage graph" errors.

Reciprocals deserve care. PoseGraph always adds h and h+180 together, so (n, h) and (n, h+180) are either both vertices or both missing. When DoTrayAssignments checks a requested destination, it retries the reciprocal after an empty lookup (scheduler.cpp:2624–:2636). That retry cannot find a vertex the first lookup missed, unless the first heading was outside [-179, 180] (say 270) and ReciprocalAngle returns a wrapped value (90); ReciprocalAngle itself is in common, which is not in the snapshots. Reciprocals matter for footprints and turns, not for vertex existence:

  • A tray or AGV is a centred rectangle, so h and h+180 cover the same floor.
  • PlanAgvMoveJob uses IsAngleOrReciprocal to skip a needless rotation when the job allows it (:749).
  • It also converts a destination into tray coordinates when the tray sits reversed on the AGV (:767–:769).
  • CollisionTable still stores h and h+180 as separate keys (a TODO in BuildTable).

CollisionTable: precomputed conflict sets

The table answers one question: if something of footprint type F stands at location a, may something of footprint type Q be at location b? A location is a pose or an edge (a move), and a footprint type is a CollisionEntityId:

  • BAY_ODP, TRAY_LEGS, TRAY and AGV;
  • one PAYLOAD id per parking window.

Nothing is computed geometrically during planning. Every answer was precomputed into four nested hash maps:

Overload Reads Returns
Query(fixed_id, queried_id, pose) ppmap_, pemap_ std::tuple<PoseSet, EdgeSet>: every pose and edge the queried entity may not use
Query(fixed_id, queried_id, edge) epmap_, eemap_ the same, for an entity moving along an edge
Query(fixed_id, queried_id, location, queried_location) -> bool one of the four maps, then find true if they conflict (four overloads: pose or edge on each side)

Things to know when you use it:

  • A missing key means "no conflict". The table cannot tell an impossible query (an id or pose that does not exist) from a pair that does not overlap; two TODOs say so.
  • Every query copies a set. Even the bool overloads copy the whole unordered_set out of the map before calling find, so a check inside a hot loop is not free.
  • The cache can go stale. The cache file name contains only the layout's name and md5. Editing the YAML forces a rebuild, but changing footprint code does not; delete ~/.cache/volley/<layout>_collision_table_<md5>.json after changing collision geometry.
  • Who calls it.
    • volley::GetStaticFilter uses it to disable vertices around occupants.
    • GarageOccupancyChecker::AddOccupant spreads each occupant to every location it blocks, using the one-location overloads.
    • DoTrayAssignments and AgvMatchingEventDeps call the bool overload directly.

ScheduledJobDataMsg: what one entry holds

ScheduledJobDataMsg is the scheduler's C++ alias for the ROS message interfaces::msg::ScheduledJobData. The response carries one per pending job, in PlanResponse.scheduled_jobs. (How Plan() builds these entries, and the internal plan_ctx->scheduled_jobs list it builds them from, is in section 13.) Each entry answers three questions for Dispatch: which job is this and how did it go (job), which actions in the schedule belong to it (node_indices), and, for a retrieve, which action is the car arriving at the bay (bay_id, bay_arrival_node_guid).

node_indices is filled by matching guids, not indices: each ActionNode carries job_id = scheduled_jobs[event->GetJobIndex()].job.guid (set in BuildActionDagFromMotions), and BuildScheduledActionsArray walks the final ordering and appends each node's position to the entry whose job.guid equals that job_id. The bay fields are found the same way: the final loop scans the nodes for a TYPE_BAY_COMMAND with COMMAND_TYPE_PROCESS_RETRIEVE and the job's guid.

ScheduleContext: the per-call workspace

DiscreteGarageState describes the garage. ScheduleContext describes one planning attempt: the garage it started from, the events planned so far, the jobs they belong to, and the maps that link those events together. Every stage of Plan() after request validation reads it, and most of them change it. When a later section says “the job method adds an edge” or “tray assignment fills the destination”, the thing being changed is a field of this object. Learning its nine fields once makes the rest of this guide much easier to follow.

Key facts:

  • One per Plan() call. Plan() creates it with std::make_shared<ScheduleContext>(...) right after the request passes validation, and it is freed when Plan() returns. Nothing in it survives to the next request; the only output is the PlanResponse built from it.
  • Shared, not copied. Every stage receives the same ScheduleContextSPtr (std::shared_ptr<ScheduleContext>). Passing the pointer by value copies the pointer, so all stages edit one object (section 9 explains why const methods can still do that).
  • A plain bag of public fields. It is declared as a class in include/scheduler/scheduler.hpp (:57–:115), but all members are public, and it enforces no invariants. Three small helper methods exist; everything else is direct field access (ctx->events.AddEvent(...)).

The four groups

Identity says which request this is and when it started. Only start_time affects the result: PlanMotions builds its ContinuousState from initial_state at start_time, so every timed motion in the response is measured from the moment the request arrived.

Fixed inputs are settled before any job is expanded. initial_state is the validated base_state, with every AGV, node, bay and VECS used by the already-running base_schedule marked disabled (section 9 shows the code). disabledness_filters precomputes, for each footprint type (CollisionEntityId: an AGV, an empty tray, a tray with a certain payload, ...), which graph vertices are unusable because of those disabled entities. Job methods consult it to reject destinations early, instead of discovering the problem in a path search. Neither field is changed after this point. Nothing enforces that (they are public and non-const), but the whole design relies on it: every “where is everything now?” question is answered by copying initial_state and replaying events on the copy.

The plan being built is the output in progress. events starts empty; job expansion adds intent, tray assignment adds blocker moves, AGV assignment adds approach, lift and lower events, and Reduce() removes redundant edges. scheduled_jobs lists the jobs that planned successfully, in planning order, so that an event's job_index can be turned back into the job it belongs to.

Bookkeeping maps hold pointers into events so that a stage can find “the last event for this AGV” or “the first move of this tray” without searching the DAG. They point at the same objects as the DAG (shared_ptr copies), so following a map entry gives you the actual vertex's event.

That is enough to read the next sections. Section 13 comes back to ScheduleContext once events (section 11) and the event DAG (section 12) have been introduced, and explains scheduled_jobs, the three helper methods and the two bookkeeping maps in depth.

One Plan() call, step by step

The job loop is a plain switch. Each case calls one Plan<Type>Job method with the index the job will have if it succeeds:

// Where: Scheduler::Plan(...) const, after plan_ctx has been created.
//   job       -> const SchedulerJobMsg&, one element of request_data.pending_jobs
//   job_index -> plan_ctx->scheduled_jobs.size(): the position this job takes if planning succeeds.
//                Every event created for the job stores it (event->GetJobIndex()).
for(const SchedulerJobMsg& job : request_data.pending_jobs) {
  switch(job.type) {
  case SchedulerJobMsg::TYPE_RETRIEVE: {
    // PlanRetrieveJob returns std::tuple<bool, std::string, bool>: success, message, retain_job
    auto [success, message, retain_job] =
        PlanRetrieveJob(plan_ctx, job.payload_id, plan_ctx->scheduled_jobs.size());
    if(!success) {
      result.scheduled_jobs.push_back(FailJob(job, message, retain_job));   // STATE_ERROR, keep going
      break;
    }
    plan_ctx->PushBackScheduledJob(job);      // now job_index really is this job's position
  } break;
  // ... one case per job type, see section 14
  }
}

  • A failed job leaves its partial events behind. FailJob only marks the job; it does not remove events that Plan<Type>Job already added to plan_ctx->events (a TODO(Joe) in FailJob says so). Most job methods validate before adding events, so this is rare, but keep it in mind when a later stage fails mysteriously.

Event types and polymorphism

A ScheduleEvent is an in-memory C++ object for one discrete state change that can be replayed against a DiscreteGarageState. The classes are in planner_core/schedule_events.hpp and src/schedule_events.cpp (in sources/repomix-planner-core.xml).

The design idea is runtime polymorphism. ctx->events stores std::shared_ptr<ScheduleEvent>, but each pointer actually points to a TrayMove, AgvMove, BayTransition, VecsTransition or VrcTransition. When the Scheduler replays the DAG, virtual dispatch runs the right Apply. When it needs subclass-specific data it checks event->GetType() and then downcasts:

// Where: the loop at the top of Scheduler::DoTrayAssignments(ScheduleContextSPtr ctx) const.
//   event_vert -> a vertex id from ctx->events.GetTopologicalOrdering() (a std::vector of vertices)
//   event      -> std::shared_ptr<volley::ScheduleEvent>; GetEventFromVertex returns an optional
auto event = ctx->events.GetEventFromVertex(event_vert).value();
if(event->GetType() != volley::ScheduleEventType::TRAY_MOVE) { /* handle bay/VECS events */ }
auto* move = dynamic_cast<volley::TrayMove*>(event.get());   // non-owning raw pointer; event keeps it alive
if(!move->GetTrayId()) { /* std::optional<uint16_t> is empty: no tray chosen yet */ }

Two confusions to avoid: inheritance says nothing about execution order, and the subclasses are siblings, not phases. A TrayMove never “turns into” an AgvMove; AGV assignment adds separate AgvMove events around it.

Four facts the rest of the guide relies on:

  • Apply is const. Replaying an event changes only the DiscreteGarageState passed in, never the event. That is why the same event objects can be replayed by every job method and every stage.
  • The job index is fixed at construction. There is no setter. Blocker moves get their index by being constructed with the root move's GetJobIndex().
  • Events can be copy-constructed but not assigned. TrayMove copy = *move; compiles; copy = *move; does not (the base copy assignment is private). Doc 02's proposal relies on the first.
  • GetGarageEntityId() drives rule A. It returns the entity whose last event a new event must wait for. A TrayMove with no tray yet returns std::nullopt, which is why such moves skip rule A (section 14.5).

Directed acyclic graphs, then ScheduleEventDag

ctx->events, a ScheduleEventDag, is the plan while Plan() runs. Job expansion writes intent into it, tray and AGV assignment extend it, Reduce() thins it, the sanity check replays it, CHUGG turns it into timed motions, and the response turns its edges into the action nodes' parent lists. This section starts with the graph theory (12.1, 12.2), then goes inside the class: its type family (12.3), what it stores (12.4), each operation (12.5), how copies behave (12.6), how the DAG grows during Plan() (12.7), what Reduce() does (12.8), and the traps (12.9).

Graph theory in one paragraph

Graph theory first. A directed graph \mathcal G=(\mathcal V,\mathcal E) has vertices \mathcal V and directed edges \mathcal E\subseteq\mathcal V\times\mathcal V. Here an edge (u,v)\in\mathcal E means event u must finish before event v may start. A DAG has no directed cycle; otherwise some event would have to finish before itself.

An ordering function \pi:\mathcal V\to\{0,\ldots,n-1\} assigns each vertex an index, where n=|\mathcal V| is the number of events. A topological order satisfies:

(u,v)\in\mathcal E\quad\Longrightarrow\quad\pi(u)<\pi(v).

What a topological ordering is, in plain words

The DAG says what must come before what, but not in which single sequence to do things. A topological ordering is such a sequence: a list of all events in which every edge points forward, so each event appears after everything it depends on. Usually there are many valid lists, because independent events (two different jobs, say) can be interleaved in any way. If the graph has a cycle, there is no valid list at all: some event would have to come before itself.

To compute one by hand, repeatedly take any event whose prerequisites have all been taken already. "Replaying the DAG" (events.Apply(working_state)) means applying events in exactly such an order.

Two consequences for the code: a pass that walks the order should not depend on which valid order it gets (ScheduleEventDag puts lower job indices first, but leaves ties within a job to a heap, 12.5), and any edge that would close a cycle makes every later pass fail with "Failed to get total ordering". That is why risky edges are guarded with WouldCreateCycle(a, b).

Three design choices explain most of the behaviour in the rest of this section:

  • boost::vecS for vertices. Vertices are plain indices 0 … n−1, so lookups by vertex are array accesses and HasVertex(v) is just v < NumVertices(). The price: removing a vertex shifts every later index down by one.
  • bidirectionalS. Each vertex stores both its in-edges and its out-edges, so GetInEdges, GetParents and in-degree checks are cheap. Rule B's leaf search and the root search both use the degrees.
  • A side map ptr_to_vertex_. Boost only maps vertex → value. DagBase keeps the reverse map itself, so “where is this event?” is a hash lookup. Every pointer-taking method goes through it, and it is why the same event cannot be added twice: Add(ptr) returns std::nullopt if ptr is already a key.

Edges, roots, leaves. An edge u → v reads “u must finish before v starts”, nothing more: not “u is near v” and not “the same AGV does both”. A root can start as soon as the plan starts; a leaf is something nothing else waits for. Rule B (section 14.5) is built on leaves: a new event of job k waits for every current leaf of job k, which is “everything job k has done so far that nothing else is waiting for”.

How ScheduleEventDag orders events. It overrides the Boost DFS sort with Kahn's algorithm:

// planner_core/src/event_dag.cpp — ScheduleEventDag::GetTopologicalOrdering (abridged)
auto vert_cmp = [this](Vertex l, Vertex r) {                      // min-heap on job index
  return GetEventFromVertex(l).value()->GetJobIndex() > GetEventFromVertex(r).value()->GetJobIndex();
};
std::priority_queue<Vertex, VertexVec, decltype(vert_cmp)> priority_q(vert_cmp);
// push every vertex with in-degree 0; then repeatedly:
//   u = lowest job index among the ready vertices; append u; decrement the in-degree of u's children;
//   push each child that reaches in-degree 0
if(count != NumVertices()) return std::nullopt;                   // some vertices never became ready: a cycle

So the order is deterministic for a given DAG built in a given order, and it prefers earlier jobs. That is a property callers may rely on (replays and walks process job 0 first), but it is not a promise about events within one job: the priority queue only compares job indices, so among equal indices the heap's internal order decides.

Replay. Apply(state) is how a stage answers “where is everything after the events planned so far?” It does not change the DAG or the events (ScheduleEvent::Apply is const); it advances the DiscreteGarageState it is given, discretely. What each event type does to the state is in section 11. Every job method starts with the same two lines:

volley::DiscreteGarageState working_state = ctx->initial_state;   // a fresh copy of the request's garage
auto [success, message] = ctx->events.Apply(working_state);       // every event so far, in topological order

Tray assignment, AGV assignment, path repair and SanityCheckEvents do the same replay by hand (walk GetTopologicalOrdering() and call event->Apply(working_state) per event), because they need to stop or act between events.

Copies share events: event_dag_copy as a work queue

DagBase declares its copy constructor = default, so copying copies dag_ and ptr_to_vertex_: new vertices and edges, but each vertex holds the same shared_ptr as the original. Changing the structure of the copy (removing a vertex) does not affect the original; changing an event through either one changes it for both. DoAgvAssignments uses exactly that combination.

// Scheduler::DoAgvAssignments (src/scheduler.cpp), structure only
auto event_dag_copy(ctx->events);                         // ScheduleEventDag: new vertices/edges, SAME event objects
while(event_dag_copy.GetRootEvents().size() > 0) {
  // phase 1: apply every non-TrayMove root to working_state, then event_dag_copy.Remove(root)
  // phase 2: BottleneckAssignment over (AGV, TrayMove root) pairs; for each match:
  //            add approach / lift events to ctx->events, tray_move->SetAgvId(agv),
  //            add edges in ctx->events, event_dag_copy.Remove(root), add the lower event
}
// then EnsureAgvMovePathsClear, ctx->events.Reduce(), AddDepsAfterAmiga for each bay / VECS transition

This is Kahn's algorithm again, done in rounds so that all tray moves that are ready at the same time are matched together. Unmatched tray-move roots stay in the copy for the next round. Each Remove renumbers the copy's later vertices, which is harmless because the loop only ever talks to the copy through event pointers. The comment above phase 1 (SW2-377) explains why all non-tray roots are drained first: a bay transition can hide a tray move that the matching must see in the same round.

Reduce(): fewer edges, same order

Reduce() computes the transitive reduction: it removes every edge u → v for which another path u → … → v exists. The set of valid orders does not change, but the graph becomes smaller and easier to read, and the response's parent lists get shorter. The stages above add edges liberally, so this matters. (The response code relies on the same idea for its action DAG: “Overkill but pruned later by Reduce()”.)

The implementation is hand-written (the boost/graph/transitive_reduction.hpp header is included but not used):

  1. Get a topological order (the job-priority one, since GetTopologicalOrdering is virtual) and each vertex's position in it. On a cycle, return {false, "The graph must be a DAG."} without changing anything.
  2. Build a V × V reachability matrix of bools, filling it in reverse topological order: u reaches each child v, and everything v reaches.
  3. Mark edge u → v redundant if u has another child w that comes before v and reaches v.
  4. Remove the marked edges.

Memory is V² bits and time is roughly O(V · E), which is fine for the tens to low hundreds of events one plan has.

Where it runs, and where it doesn't:

  • Not after tray assignment. The call is commented out with “TODO(Gunther): Reduce here breaks the AgvAssignments for some reason.”
  • At the end of AGV assignment, before AddDepsAfterAmiga.
  • Again in Plan(), before SanityCheckEvents, with “TODO(any) Planning may fail if Reduce() is not called”.

Both calls discard the returned BoolStringPair, so a cyclic DAG at that point is not reported by Reduce(); the next GetTopologicalOrdering() catches it. Nobody has written down why the placement matters (doc 02, risk 2). Doc 02, risk 3, gives a likely reason for the tray-assignment case: two AGV-assignment helpers look only at direct edges, which Reduce() may replace with longer paths. A test shows the visible effect: after DoAgvAssignments, the direct edges tray_move_1 → tray_move_2 that the test added are gone (EXPECT_FALSE(ctx->events.HasDependency(...))), because the AGV chains now imply them. HasDependency checks a direct edge only, so after Reduce() it is the wrong question for “must a finish before b?”.

Gotchas

  • Never remove a vertex from ctx->events. Vertex indices are how CHUGG's motions find their events again, and removal shifts every later index. Removing from a copy is fine; that is what the copy is for.
  • A copy is not a snapshot of the events. auto copy(ctx->events) shares every event object. To compare “before” and “after” a stage (as the parity tests in doc 03 must), build two contexts independently.
  • AddDependency fails silently. It returns false when either endpoint was never added (a forgotten AddEvent) or the edge exists, and almost every caller ignores the result. A missing AddEvent therefore means a missing edge, not an error.
  • Not every edge is cycle-checked, and the check needs both events present. AddDependency never checks for cycles. Only the two risky AGV-assignment edges ask WouldCreateCycle first, and it answers false (safe) if either endpoint is missing. Everything else relies on the stage-end GetTopologicalOrdering() check, which reports that there is a cycle, not which edge closed it. When debugging one, dump the graph with debug/printdags (section 22).
  • Order is by job index, then heap order. GetTopologicalOrdering() and GetRootEvents() both prefer lower job indices. Within one job, GetRootEvents() uses std::sort (not stable) and the topological sort uses a heap, so code must not assume anything about the order of same-job events beyond what the edges force.
  • Apply stops at the first failing event. The state has then been advanced by every event before it. Job methods return the error, but working_state is already partly replayed.
  • Replays are repeated, not cached. Each job method copies initial_state and replays the whole DAG, nested calls replay again, and AddDepsAfterAmiga recomputes a topological order and replays from scratch for each dependency it inspects. This is simple and correct, but cost grows with the square of the number of events.
  • Lookups assume membership. Most call sites write GetEventFromVertex(v).value(), which throws std::bad_optional_access for an out-of-range vertex; GetInEdges / GetOutEdges throw std::invalid_argument. PropagateEventCostToChildren throws its own std::runtime_error("Failed to get AGV vertex in DAG") when an event is missing.

scheduled_jobs in detail

There are two vectors of ScheduledJobDataMsg in Plan(), and Figure 23 tracks both:

  • plan_ctx->scheduled_jobs. plan_ctx is a ScheduleContextSPtr (std::shared_ptr<ScheduleContext>), created at the top of Plan(). Its scheduled_jobs holds only the jobs that planned successfully, in planning order. This is the internal table that turns an event's job_index back into a job.
  • result.scheduled_jobs. result is the PlanResponseMsg that Plan() declares as a local at its top and returns at the end; SchedulerRos copies it into the service response. Its scheduled_jobs is the output list.

During the job loop each request_data.pending_jobs[i] goes to exactly one of the two: to plan_ctx->scheduled_jobs if its job method succeeds, to result.scheduled_jobs (via FailJob) if it fails. After motion planning, the final loop copies every planned entry into result.scheduled_jobs as well, so the response ends with every job, failures first.

“Expanding” a job means calling its job method, Plan<Type>Job(plan_ctx, <job's arguments>, job_index) (PlanRetrieveJob, PlanInsertJob, PlanReparkTrayJob, ...). The method replays plan_ctx->events onto a copy of initial_state to find where everything is, then adds new ScheduleEvents and dependency edges directly into plan_ctx->events (and updates last_entity_event / first_tray_event). It returns only {success, message, retain_job}. It does not touch either scheduled_jobs vector; Plan() does that from the return value.

Every ScheduleEvent stores a job_index, set when the event is constructed (std::make_shared<TrayMove>(job_index)). Plan() passes plan_ctx->scheduled_jobs.size() as the job_index of the job it is about to expand, and pushes the job onto scheduled_jobs only if expansion succeeds:

// Scheduler::Plan, the job loop (src/scheduler.cpp:454 onwards), one case shown
case SchedulerJobMsg::TYPE_RETRIEVE: {
  auto [success, message, retain_job] =
      PlanRetrieveJob(plan_ctx, job.payload_id, plan_ctx->scheduled_jobs.size());  // job_index = current size
  if(!success) {
    result.scheduled_jobs.push_back(FailJob(job, message, retain_job));  // reported failed; NOT pushed to ctx
    break;
  }
  plan_ctx->PushBackScheduledJob(job);                                    // now scheduled_jobs[job_index] == job
} break;

So scheduled_jobs[k] is the job whose events carry job_index == k. Four places rely on that:

Where What it does with the index
Job methods Stamp every event they create with their job_index; nested calls (PlanRetrieveJob → PlanReparkTrayJob) pass the same index down
Rule B, UpdateLeafDependencies Only links leaves whose GetJobIndex() equals the new event's job
Tray assignment Builds every blocker move as TrayMove(move->GetJobIndex()), so blockers belong to the job they unblock
BuildActionDagFromMotions Labels each action with ctx->scheduled_jobs[event->GetJobIndex()].job.guid, which is how Dispatch learns which job an action serves

Three consequences:

  • Composite jobs share one index. The repark inside a retrieve, and every blocker move tray assignment adds for it, report as part of the retrieve (section 14.6).
  • A failed job's index is reused. The failed job is not pushed, so the next job gets the same index. If the failed job left events behind in events, they now appear to belong to the next job (section 14.18, gotcha 1). FailJob itself only builds the response entry (state = STATE_ERROR, note = message, retain_job); a TODO(Joe) in it says it should also remove the failed job's events.
  • The correspondence ends at the very end. BuildScheduledActionsArray copies the vector into an unordered_map keyed by job guid, appends each action's position to its job's node_indices, then clears the vector and refills it from the map. After that, entry k is no longer the job with index k. Nothing reads it by index any more, but the order reaches the response: result.scheduled_jobs lists the failed jobs first (pushed during the loop) and then the planned ones in hash-map order, not request order.

    events.AddDependency(last_entity_event.at(entity_id), new_event);   // previous event -> new event
  }
  last_entity_event[entity_id] = new_event;                             // new event is now the last
}

// Rule B (section 14.5): the new event waits for every current leaf of the SAME job.
void UpdateLeafDependencies(const ScheduleEventSPtr& childevent, size_t job_index) {
  for(const auto& leaf_event : events.GetLeafEvents()) {               // leaf = no outgoing edge
    if(leaf_event == childevent) continue;
    if(leaf_event->GetJobIndex() == job_index) {
      events.AddDependency(leaf_event, childevent);
    }
  }
}

The two Update... methods are the only code in ScheduleContext that adds edges. Both assume the event has already been added with ctx->events.AddEvent(e); if it has not, AddDependency returns false and the edge is silently lost (section 12.5). GarageEntityIdMsg is a ROS message holding an asset type letter and an id; the code builds keys with volley::AgvId(id), TrayId(id), BayId(id) and VecsId(id).

last_entity_event in detail

last_entity_event is a std::unordered_map<GarageEntityIdMsg, ScheduleEventSPtr>: for each AGV, tray, bay and VECS, the last event added so far that touches it. It exists for one purpose, rule A: when a job method adds an event for entity X, that event must wait for whatever X was last asked to do, even if a different job asked. Without it, two jobs that both move tray T19 could run in either order.

How it is keyed, written and read:

  • Keys are GarageEntityIdMsg values (asset type letter plus id) built with volley::AgvId(id), TrayId(id), BayId(id), VecsId(id). Job methods take the key from event->GetGarageEntityId(): a TrayMove gives its tray, an AgvMove its AGV, a BayTransition its bay, a VecsTransition its VECS. A TrayMove with no tray yet has no key (std::nullopt) and skips rule A.
  • Written only by UpdateLastEntityEvent(key, e): add the edge last[key] → e if key is present, then set last[key] = e. The entry always moves forward; nothing ever removes one.
  • Read in two places: inside UpdateLastEntityEvent (rule A), and by rule C in PlanReparkTrayJob, which checks find(BayId(...)) / find(VecsId(...)) and adds last[bay] → tray_move without updating the map (so the bay's chain is not moved forward by a tray entering it).

Why later stages do not use it: tray assignment adds blocker moves and AGV assignment adds approach, lift and lower moves, and neither calls UpdateLastEntityEvent. The map is therefore only correct while jobs are being expanded. Tray assignment keeps its own last_tray_event (local to DoTrayAssignments) and AGV assignment its own last_agv_event, each built from scratch as that stage walks the DAG. Reading ctx->last_entity_event after stage 3 would give an answer that ignores every event those stages added.

first_tray_event in detail

first_tray_event is a std::unordered_map<uint16_t, ScheduleEventSPtr>, keyed by tray id: for each tray that moves at all, the first move that takes it off the node it started on. It is the only hand-off between tray assignment and AGV assignment, and it answers one question for AGV assignment: “when is this tray gone from its starting node?”

Written by tray assignment, in two places with the same pattern (the main loop and AssignDestForUntargetedMove), for every tray move it processes, including the blocker moves it creates:

// src/scheduler.cpp, DoTrayAssignments (and AssignDestForUntargetedMove)
if(last_tray_event.find(tray_id) != last_tray_event.end()) {
  ctx->events.AddDependency(last_tray_event[tray_id], move);   // later move of the same tray: chain it
} else {
  ctx->first_tray_event[tray_id] = move;                       // the first move of this tray in the plan
}
last_tray_event[tray_id] = move;

Read by AGV assignment, in MoveAgvToTrayPose, when an AGV has to drive to a tray it will carry:

// src/scheduler.cpp, MoveAgvToTrayPose (abridged)
auto nav_path = volley::GetPosePath(gg_, agv.pose, tray.pose, cost_model_);   // the AGV's route to the tray
for(size_t i = 1; i < nav_path.size(); ++i) {
  const uint16_t path_node = nav_path[i].node_id;
  if(path_node == tray.pose.node_id) continue;                          // the destination itself is fine
  for(const auto& [blocker_id, blocker] : ctx->initial_state.GetTrays()) {
    if(blocker.pose.node_id != path_node) continue;                      // a tray STARTED on this node
    auto it = ctx->first_tray_event.find(blocker_id);
    if(it == ctx->first_tray_event.end()) break;                         // it never moves: nothing to wait for
    if(!ctx->events.WouldCreateCycle(it->second, root_event)) {
      ctx->events.AddDependency(it->second, move_to_tray);              // drive through only after it left
    }
    break;
  }
}

Three details:

  • Starting nodes come from initial_state. The map only knows when a tray leaves its original node. A tray that moves onto the AGV's path later is not covered by this rule; if that makes the route impossible, SanityCheckEvents rejects the plan ("Cannot find path ...", section 18).
  • Why the first move, not the last. The comment on the field says it: using the last move “would create a cycle when a tray is moved multiple times by the same AGV in one plan”. The figure shows the case: the AGV that must wait is the same AGV that later moves the tray again.
  • The cycle check uses the root event. move_to_tray has no children yet when the edge is added, so WouldCreateCycle(first, move_to_tray) would always say “safe”. The code asks about root_event (the tray move this approach leads to) instead, because move_to_tray will reach it through the task-chain edges added next (the lift, then the tray move itself).

Life cycle across one Plan() call

The columns are the stages of section 10:

  1. Construct. Identity fields and initial_state are set; events, scheduled_jobs and the maps start empty.
  2. Filters. disabledness_filters is computed from initial_state.
  3. Job expansion (section 14). For each pending job: copy initial_state, replay events to get working_state, add events, add edges through rules A, B and C, then push the job onto scheduled_jobs.
  4. Tray assignment (section 16). Copies initial_state, walks events in topological order, fills blank fields, adds blocker moves and edges, and records first_tray_event.
  5. AGV assignment (section 17). Copies initial_state, matches AGVs, adds AGV events and edges, using first_tray_event to wait for blocking trays to leave.
  6. Reduce and sanity check (section 18). events.Reduce() drops redundant edges; SanityCheckEvents replays the DAG on a copy of initial_state and checks each move with IsMovePossible, which reads disabledness_filters.
  7. Motion planning (section 19). PlanMotions builds timed trajectories from initial_state, start_time and events.
  8. Build response. ResponseFromTrajectories turns trajectories into action nodes, labels them through scheduled_jobs, and rebuilds scheduled_jobs with node_indices.
  9. Fill result. Plan() copies each scheduled_jobs entry into result.scheduled_jobs with state STATE_EXECUTING. Then plan_ctx goes out of scope and the context is freed.

Gotchas

  • last_entity_event is stale after job expansion. Tray and AGV assignment add many events (blocker moves, AGV moves, lifts) without updating it. Code in those stages that needs “the last event of X” keeps its own local map instead (last_tray_event in tray assignment, last_agv_event in AGV assignment). Do not read ctx->last_entity_event after stage 3.
  • first_tray_event is empty until tray assignment. A job method that read it would always find nothing.
  • disabledness_filters[id] uses operator[]. If a collision-entity id has no entry, unordered_map::operator[] inserts a default-constructed GraphFilterProperties and returns that. What a default filter allows is defined in motion_planner (not in this snapshot); check it before relying on a lookup for an unusual asset type.
  • Nothing is const, nothing is private. Any function with the pointer can change initial_state or scheduled_jobs. The code base keeps to the conventions above, but the compiler does not check them. The refactor proposal in doc 02 (sections 6.1 and 6.5) narrows this for tray assignment by passing const references and returning a result.
  • A failure inside a stage leaves partial changes. Job methods that fail after adding events, and tray or AGV assignment failing halfway, leave events partly edited. Plan() handles the second case by failing every job and returning, so the half-edited context is simply discarded; the first case is gotcha 1 in section 14.18.

Job expansion: from jobs to events

Job expansion is the first planning stage inside Plan(). It turns each line of the request ("retrieve this car", "move this tray") into a handful of ScheduleEvent objects in plan_ctx->events, connected by dependency edges. It decides what has to happen and in which order. It does not decide how (no paths, no timing) or by whom (no AGV is chosen, except in one case).

A useful picture: each job method is a recipe. It writes a few cards (events) onto a shared board (the event DAG) and ties strings (edges) between cards that must happen one after another. Later stages fill in the blanks on the cards and add more cards and strings.

The loop in Plan()

What the code does, in order

Plan() turns one PlanRequestMsg into one PlanResponseMsg. Job expansion is the loop in the middle of it. Around the loop, Plan() does this:

  1. Build the starting point. ValidateBaseState() turns request_data.base_state into a DiscreteGarageState. Entities used by actions that are already executing (request_data.base_schedule) are marked disabled. A fresh ScheduleContext is created: plan_ctx, with an empty event DAG and an empty scheduled_jobs list.
  2. Expand every pending job (this section). The job method writes its events directly into plan_ctx->events (it does not return them) and returns only success or failure. On success, Plan() appends the job to plan_ctx->scheduled_jobs; on failure, it reports the job in result.scheduled_jobs. Which arguments are read and which are changed is shown in 14.3.
  3. Plan all successful jobs together: tray assignment, AGV assignment, Reduce(), sanity check, motion planning (sections 16 to 18). From here on the jobs are no longer separate: one DAG holds all their events, and the later stages see and optimise all of them at once.
  4. Write the response. Every motion becomes an ActionNode labelled with its job's guid. Each successful job gets state = STATE_EXECUTING and node_indices (the positions of its actions), and is appended to result.scheduled_jobs after the failed ones.

The loop itself:

// src/scheduler.cpp — inside PlanResponseMsg Scheduler::Plan(const PlanRequestMsg& request_data,
//                                                            const rclcpp::Time& now) const
// this     : const Scheduler*
// plan_ctx : ScheduleContextSPtr — built a few lines earlier from request_data.base_state
// result   : PlanResponseMsg — what Plan() will return
for(const SchedulerJobMsg& job : request_data.pending_jobs) {        // in request order
  switch(job.type) {
  case SchedulerJobMsg::TYPE_RETRIEVE: {
    auto [success, message, retain_job] =                            // the only 3-value job method
        PlanRetrieveJob(plan_ctx, job.payload_id, plan_ctx->scheduled_jobs.size());
    if(!success) {
      result.scheduled_jobs.push_back(FailJob(job, message, retain_job));  // reported now
      break;                                                         // leaves the switch, not the loop
    }
    plan_ctx->PushBackScheduledJob(job);                             // job_index is now "taken"
  } break;
  case SchedulerJobMsg::TYPE_REPARK_TRAY:
  case SchedulerJobMsg::TYPE_MOVE_TRAY: {                            // two types, one method
    auto [success, message] = PlanReparkTrayJob(plan_ctx, job.tray_id,
        plan_ctx->scheduled_jobs.size(), job.allow_reciprocal, job.destination);
    ...
  } break;
  // ... one case per job type; an unknown type is failed with "Unknown job type"
  }
}

How job_index works

One job almost always creates several events. A RETRIEVE creates up to five (stop charging, open the bay, move the tray already in the bay out, move the car's tray in, hand the car over); a REPARK_TRAY creates one (two if the tray must first stop charging); a REBALANCE_GARAGE creates a few per bay it switches. Every one of them belongs to the same job. Sections 14.7 to 14.17 list what each job type creates.

So every event needs to remember which job it belongs to, and the response needs to say "this action is part of job X". The code does not store the job's guid in the event. Each event is constructed with a small integer, the job_index, and the job is looked up from it at the end:

// inside PlanRetrieveJob(ScheduleContextSPtr ctx, const GuidMsg& payload_id, size_t job_index)
auto bay_transition = std::make_shared<BayTransition>(job_index, *bay_opt, cmd);  // tagged with job_index
...
PlanReparkTrayJob(ctx, payload_opt->tray_id, job_index, false, dest_pose);        // its TrayMove: same tag
...
auto process = std::make_shared<BayTransition>(job_index, *bay_opt, cmd);         // same tag again

The relationship is one job → many events → many actions:

Level How many How it points to the job
Job one entry in plan_ctx->scheduled_jobs its position in that list is the job_index
Events all events the job method creates, plus the ones later stages add for it event->GetJobIndex(). Tray assignment builds blocker moves as TrayMove(move->GetJobIndex()) and AGV assignment builds approach moves as AgvMove(root_event->GetJobIndex(), ...), so they inherit the index of the move that needed them
Actions one ActionNode per motion of those events job_id = the job's guid; the job's node_indices list their positions
  • What the number is. job_index is the job's position in plan_ctx->scheduled_jobs, the list of jobs that have succeeded so far. It is not the loop counter (the job's position in request_data.pending_jobs).
  • How it is chosen. Just before calling the job method, Plan() passes plan_ctx->scheduled_jobs.size(). If the method succeeds, PushBackScheduledJob(job) appends the job at exactly that position, so scheduled_jobs[job_index] is now this job. If it fails, nothing is appended and the next job is offered the same number.
  • How it is used. When the response is built, ToActionNode(motion, ctx->scheduled_jobs[event->GetJobIndex()].job.guid, event) turns the index back into the job's guid. Rule B (14.5) also compares indices to decide which events belong to the same job.

Why it is built this way

The code has no design document, so this is a reading of the structure, with the trade-offs it implies.

  • Plan() is a pure function of the request. Nothing survives between calls except the fixed layout, graph and collision table. Dispatch owns the job queue and the live garage state and sends both every time. That keeps the scheduler simple to test (build a request, call Plan(), inspect the response) and lets Dispatch replan whenever something changes.
  • Jobs are expanded one at a time, in request order, each seeing the garage that earlier jobs leave behind (14.4). That is a greedy approach: easy to reason about, and later jobs automatically build on earlier ones (a second move of the same tray starts where the first one ends). The cost is that request order matters and nothing tries another order: an early job can make a later one fail, and the later one is simply reported as failed.
  • Failure is per job during expansion. One bad job does not sink the others, so Dispatch still gets a plan for everything that was possible. retain_job lets RETRIEVE say "try me again later" when no bay is free.
  • After expansion, everything is one problem. All successful jobs share one DAG, so tray assignment, AGV assignment and motion planning can share AGVs and resolve conflicts across jobs. The flip side is in section 10: if any later stage fails, every pending job is failed.
  • A small integer instead of a pointer or guid. Events are planner_core objects that know nothing about ROS messages. A size_t is the cheapest way to tag them and is enough for rule B's "same job?" test.

Known issues with this design (details in 14.18):

  • No rollback. A job method that fails after adding events leaves them in the DAG. They keep the failed job's index, which the next successful job reuses, so they are executed as part of that job (or, if no later job succeeds, scheduled_jobs[index] reads past the end). FailJob() carries a TODO to strip them.
  • Index reuse makes logs confusing. "Job index 1" means different requests at different moments of one Plan() call.
  • Order dependence without a retry. The plan depends on the order Dispatch lists the jobs, and a failed job is not retried after the others are placed.
  • Duplicate failures. When a later stage fails, Plan() fails every job in pending_jobs, including jobs already reported failed by the loop.

Possible directions (ideas, not plans): tag events with the job's guid instead of a position; take a snapshot of events, last_entity_event and first_tray_event before each job and restore it on failure; or plan each job into a separate small DAG and merge it only on success.

The shape of every job method

// ctx  : the same ScheduleContextSPtr as plan_ctx in Plan(); the method edits *ctx

// (1) See the garage as all earlier events leave it (14.4)
volley::DiscreteGarageState working_state = ctx->initial_state;     // a copy
auto [success, message] = ctx->events.Apply(working_state);         // replay the whole DAG

// (2) Look up what the job names. Lookups return std::optional<...Msg>
std::optional<DiscreteBayStateMsg> bay_opt = working_state.GetBay(bay_id);

// (3) Check preconditions; return early with a message if one fails
if(!bay_opt.has_value() || bay_opt->disabled) {
  return std::make_pair(false, "...");
}

ctx->events.AddEvent(bay_transition);

std::tie(success, message) = PlanReparkTrayJob(ctx, tray_id, job_index, /*allow_recip=*/true);

Two more effects are easy to miss:

  • Some job methods talk to Dispatch. PlanInsertJob calls reset_bay_state_request_fn_, which SchedulerRos wired to an asynchronous ROS service request (TransitionBayToInsert). It is sent during expansion, before anyone knows whether the whole plan will succeed. Plan() itself calls clean_garage_request_fn_() when an INSERT fails.

Is this a good design?

It is a common C++ style, and it has real reasons behind it, but it makes the code harder to follow, and it is the root of several gotchas in 14.18. A fair summary:

Why it was probably written this way

  • One growing structure is convenient. Every step needs the latest DAG and the latest last_entity_event. Passing one context pointer around is less code than threading inputs and results through every call.
  • Composition is free. When PlanRetrieveJob calls PlanReparkTrayJob, the inner method simply appends to the same DAG, and its events immediately take part in rule B for the outer job. With pure functions, the caller has to merge the inner result itself.
  • The later stages really are graph rewrites. Tray and AGV assignment fill in fields of existing events, add events and add edges across all jobs. In-place editing is natural there, and job expansion uses the same style for consistency.
  • Events are shared objects (std::shared_ptr). Producing a modified copy of a DAG would need deep copies, so mutation is the cheap option. (Doc 02, sections 6.1 and 6.5, show a middle way for tray assignment: return an ordered log of edits and let one function apply it.)

What it costs

  • The signature hides the output. Nothing in std::tuple<bool, std::string, bool> PlanRetrieveJob(ScheduleContextSPtr, const GuidMsg&, size_t) says "adds events and edges". You have to read the body, and the bodies of everything it calls.
  • No transaction. A method that fails halfway leaves its partial changes in *ctx (14.18, gotcha 1). A pure function that returns its events would make "discard on failure" automatic.
  • Hidden dependencies between calls. Rule B looks at the current leaves of the whole DAG, and rule A at the current last_entity_event. The result of a call therefore depends on everything that ran before it, not only on its arguments.
  • Harder to test. A test has to build a ScheduleContext, call the method, then inspect the context (see doc 03). It cannot simply compare a returned value.
  • Effects leave the process. A callback to Dispatch from inside planning cannot be undone if the plan later fails.

A purer alternative (sketched in the figure; not in the code): give each job method a read-only view (const working state, DAG, last-entity map) and have it return a JobPlan: its new events, the edges it wants (with the rule that justified each), and any follow-up requests for Dispatch. Plan() then commits a successful JobPlan into the context in one place, or drops it on failure. That makes the output visible, makes rollback automatic, and lets a test compare JobPlan values directly. The costs are some boilerplate and a Commit() step that applies rules A, B and C centrally. Two middle grounds are cheaper:

  • keep mutation but pass exactly what is changed (ScheduleEventDag& events, LastEntityMap& last) instead of the whole context, so the signature tells the truth;
  • keep the current code but snapshot events and last_entity_event before each job and restore them on failure.

Doc 02 makes the same trade-off for the tray and AGV solvers: it keeps in-place mutation for the first behaviour-preserving step and suggests a returned result afterwards.

Every job sees the garage through working_state

Three details matter in practice:

  • Apply() is discrete. A tray "teleports" to its destination; time and paths do not exist yet. Blank fields are not neutral (section 11): a TrayMove with no tray id does nothing, one with no destination removes the tray and its payload from working_state, and a tray already sitting on a destination is moved to the placeholder pose {node_id: 0, heading: 0}. So a later job does not see an empty tray that READY_FOR_INSERT will bring into a bay, and does not see a tray whose destination is still open.
  • Nested calls replay again. When PlanRetrieveJob calls PlanReparkTrayJob, the inner call copies and replays too, so it already sees the bay transition the outer method has just added.
  • The cost is repeated replay. Each job method replays the whole DAG, and nested calls replay it again. The code accepts this for simplicity.

Where the edges come from

Precisely (the letters A, B and C are this guide's shorthand; the code uses the function names, see the FAQ in section 25):

  • Rule A — same entity. ctx->last_entity_event is a map from GarageEntityIdMsg (which AGV, tray, bay or VECS) to the last event that touched it. UpdateLastEntityEvent(id, e) adds the edge last[id] -> e if there is one, then sets last[id] = e. This is the only rule that links different jobs: if job 0 and job 1 both move tray T19, job 1's move waits for job 0's.
  • Rule B — earlier leaves of the same job. A leaf is an event with no outgoing edge anywhere in the DAG. UpdateLeafDependencies(e, job_index) adds leaf -> e for every leaf whose GetJobIndex() == job_index. Within one job this makes each new event wait for "everything the job has done so far that nothing else waits for". It never links different jobs.
  • Rule C — into a bay or VECS. Only in PlanReparkTrayJob: if a TrayMove's destination is a bay (or VECS), it gets an edge from that bay's (or VECS's) last event, so a tray never enters a bay before the bay's transition. Rule C reads last_entity_event but does not update it.

Not every event goes through every rule:

  • Without rule A: a TrayMove with no tray yet (its tray is unknown); the "stop charging" VecsTransition in RETRIEVE and REPARK; and the TrayMove that MOVE_AGV creates for a loaded AGV is chained by tray only, not by AGV.
  • Without rule B: the "stop charging" VecsTransition; RETRIEVE's TRANSITION_TO_RETRIEVE (so it does not wait for that stop-charging event); CHARGE_AGV's transition that frees a trapped AGV; and CLEAN_GARAGE's hide AgvMoves. Each of these is either the first event of its job or deliberately independent, but later events of the same job still wait for them through rule B. And none of the rules knows about geometry: whether tray T15 is in the way of T17's path, or whether two AGVs would meet, is discovered and turned into edges by tray and AGV assignment (sections 16 and 17).

Job methods are built from a few shared pieces

Two patterns stand out:

  • PlanReparkTrayJob is the workhorse. Six methods create their TrayMoves through it, so the heading policy, the VECS checks and rule C live in one place. That is why it is explained first (14.7).
  • Composite jobs pass their own job_index down. When PlanRetrieveJob calls PlanReparkTrayJob(ctx, tray, job_index, ...), the inner events belong to the retrieve job. Rule B then orders them with the retrieve's other events, and the response reports them as part of the retrieve.

The order of 14.7 to 14.17 follows that structure: the building blocks first, then the jobs made from them.

Gotchas

These are behaviours of the current code that surprise people. They are not fixed here; changing them changes plans.

  1. A failed job can leave events behind. Plan() does not remove events when a job method fails, and FailJob() carries a TODO about it ("strip all the events which may be in the dag for the now failed job"). It happens when a method has already added something before a later check fails, for example:

    • RETRIEVE adds "stop charging" and then finds no bay;
    • RETRIEVE or INSERT opens a bay and then the repark fails;
    • CHARGE_AGV opens a bay and then finds no charger.

    The leftover events keep the failed job's job_index, which the next successful job reuses (14.2), so they are reported and executed as part of that job. Because they share the index, they also count as that job's leaves, so its first events get rule B edges from them. If an earlier job succeeded but no job from the failed one onward does, ctx->scheduled_jobs[event->GetJobIndex()] reads past the end of the vector when the response is built. Other places it can happen: CHARGE_AGV when the final bay transition fails, READY_FOR_INSERT when the charge-payload recipe succeeds and the empty-tray repark fails, READY_FOR_RETRIEVE when the door opens and the repark fails, and inside REBALANCE, where a bay recipe's partial events stay under the (always successful) rebalance job.

  2. PlanReparkTrayJob looks the tray up in ctx->initial_state. The "already at destination" check therefore compares with the tray's position in the request, not after earlier jobs, and the "is it on a charging VECS" check looks at the request node too.

  3. PlanReparkTrayJob with no tray but a destination reads an empty optional. The line if(tray_opt->pose == dest.value()) runs even when tray_id is std::nullopt (READY_FOR_INSERT's "any empty tray" case). That is undefined behaviour; it should test tray_opt first.

  4. job_index == 0 means "first successful job". CLEAN_GARAGE hides AGVs only then. If earlier jobs in the request failed, a later CLEAN_GARAGE can still get index 0.

  5. Bay transitions are not always necessary ones. PlanOpenBayDoor (INSERT) adds TRANSITION_TO_RETRIEVE even when the bay is already READY_TO_RETRIEVE.

  6. CHARGE_PAYLOAD throws away the unblocking moves that ResolveBlockingTrays() returns (auto [dest, _] = ...). They are found again in tray assignment.

  7. "Free charger" only means "no AGV on the node". The code says so, with a TODO to check for other conflicts.

  8. Rule B serialises composite jobs. REBALANCE_GARAGE's per-bay recipes share one job_index, so each bay waits for the previous bay's work.

  9. Some bay commands skip the disabled check. PlanReadyForInsertJob, PlanReadyForRetrieveJob, PlanOpenBayDoor and CHARGE_AGV's trapped-bay branch never test bay.disabled (INSERT and TRANSITION_BAY_TO_* do). Plan() marks bays that already have a command in base_schedule as disabled, so those methods can command such a bay again; READY_FOR_INSERT is only stopped indirectly, because the repark into a disabled bay fails.

  10. INSERT's callback fires before the plan is known to succeed. reset_bay_state_request_fn_ runs during job expansion, so Dispatch receives the refill request even if tray assignment or motion planning later fails the whole plan.

  11. Late failures duplicate failed jobs. When a later stage fails, Plan() calls FailJob for every entry of request_data.pending_jobs, including jobs that already failed in the loop, so result.scheduled_jobs can list the same job twice.

  12. AssignTrayIdForEmptyMove may change the destination heading to the chosen tray's heading when the two are the same or opposite, to avoid a rotation.

Cheat sheet and self-check

Check yourself before moving on:

  1. A request has [RETRIEVE (fails), MOVE_AGV, REPARK_TRAY]. What job_index does each successful job get?
  2. Job 0 reparks T19 to P24 and job 1 reparks T19 to P23. Which rule orders the two moves, and why does rule B not?
  3. In the retrieve figure, why does event 3 have edges from both 1 and 2?
  4. Which job types can leave a TrayMove with no destination? With no tray?
  5. Why can a bay's ODP check fail for TRANSITION_BAY_TO_INSERT but not for INSERT?
Answers
  1. MOVE_AGV gets 0 and REPARK_TRAY gets 1; the failed retrieve uses no index (but see gotcha 1 if it added events first).
  2. Rule A (same tray). Rule B only links events of the same job.
  3. Rule B (2 was the job's only leaf) and rule C (the tray is going into bay B21, whose last event is 1).
  4. No destination: RETRIEVE, INSERT, READY_FOR_RETRIEVE, CLEAN_GARAGE (and REBALANCE through READY_FOR_RETRIEVE). No tray: READY_FOR_INSERT (and REBALANCE through it) when AssignTrayIdForEmptyMove finds nothing.
  5. The ODP check lives in PlanBayTransitionJob; INSERT uses PlanOpenBayDoor, which does not check it.

Before the details of each stage, here is one retrieve followed through all three passes over the event DAG.

The problem this stage solves

Job expansion (section 14) turns each job into events, but those events describe intent, not a finished plan. Two things are still missing when expansion ends.

1. Some TrayMove events have blank fields. Every physical tray in the garage has an id, and the scheduler always knows where it is. The blank is not on a tray; it is on an event. 2. Destinations are often unreachable as the garage stands. The garage is dense: trays park nose-to-tail, and a tray can only travel through nodes that are free. Two terms are used throughout this section:

  • The root tray is the tray of the TrayMove currently being processed: the tray a job actually asked to move (a car to retrieve, an empty tray for a bay).
  • A blocking tray is any other tray whose footprint collides with the root tray's path to its destination (collision is decided by the CollisionTable, section 3, not just equal node ids). It must move out of the way first. No job asked for that move; this stage invents it.

When DoTrayAssignments(ctx) returns {true, ""}, three things hold:

  • every TrayMove in ctx->events has a tray id and a destination;
  • every blocking tray has its own new TrayMove, ordered before the move it unblocks;
  • the DAG has edges that keep moves from entering space before it is freed (freeing_moves, below), and ctx->first_tray_event records the first move of each tray for AGV assignment.

The rest of the section follows one event through the stage: the overall flow (Figure 46), the main blocking-tray loop for a move that already has both fields, then the two helpers that fill a blank tray id and a blank destination, and finally how occupancy becomes DAG edges.

Per event, in topological order (scheduler.cpp:2533):

  1. Not a TrayMove (bay / VECS transitions, AGV events): ApplyTransitionToFreeingMoves records the bay or VECS pose as occupied by that event, applies it to working_state, and moves on.
  2. Tray id blank → AssignTrayIdForEmptyMove (:2575) picks a tray; the event then continues down this list with both fields set.
  3. Destination blank → AssignDestForUntargetedMove (:2584) picks a destination, emits the blocker moves, and the loop continues: the main loop below is skipped for this event.
  4. Both set → the main blocking-tray loop.

The blocking-tray loop

This is what happens to a TrayMove that has both a tray id and a destination, such as “R: P17 → B21”. The loop is long in the source (about 450 lines), but it does five things in order:

  1. Check the destination (:2622–:2648). Build a filter that ignores every tray and AGV (trays will be moved, AGVs will drive away) and check that the destination vertex is enabled. If it is not, the job fails with “… but it's occupied, or not enabled.” “Occupied” here means something that will not move out of the way: a disabled node, a disabled tray or AGV, or a static object; ordinary trays and AGVs are ignored.
  2. Find the critical path (:2660–:2706). Search from the root tray to the destination with BlockingTraySearchEnvironment. Unlike a normal path search, this one may pass through trays; it records them. The result is the critical path (the nodes R will travel over) and blocking_trays, the trays on it, in path order.
  3. Resolve blockers one at a time (while(!blocking_trays.empty()), :2717). For the first blocker, ask ResolveBlockingTrays for a new home that is not on the critical path and does not require moving R. Two fallbacks follow if that fails (below).
  4. Turn the answer into events (:2928–:2990). Add each required move and the blocker's own move to the DAG, chained in order, with freeing_moves edges along their paths, and finally an edge “blocker move → root move”. Then re-scan the rest of the critical path for blockers and repeat step 3.
  5. Finish the root move (:3024 onwards). Add freeing_moves edges for the destination and source poses, register the source pose, apply the move to working_state, and chain it after the tray's previous move.

The two fallbacks (:2796 and :2865). If ResolveBlockingTrays returns no destination, the loop first tries to advance the root tray one step along its critical path: if no other tray collides with the next pose (table_.Query(...)), it creates a one-step TrayMove for R, applies it, removes R's old vertex from critical_path, and retries the blocker. Advancing frees the node R was on, which can give the blocker somewhere to go (the source comment draws three such cases). If that still fails, it retries with WithPriorDests(blocking_tray_id, {}): the blocker may now park on the critical path. That is allowed because the loop re-scans afterwards, so a blocker parked ahead of R is simply found and moved again. If even that fails, the job fails with “Failed to find open space for blocking tray t…”.

Turning the answer into events. required_moves (any prerequisite moves, possibly an advance of R) plus a new TrayMove for the blocker are applied to working_state in order and added to ctx->events, each depending on the one before (last_move). Each also depends on the previous move of the same tray (last_tray_event) and on whichever earlier events used poses along its path (freeing_moves.GetBlockers). The blocker's move is then made a prerequisite of the root move: ctx->events.AddDependency(new_move, event). Finally the loop walks the remaining critical path again, asks table_.Query which trays still collide with it, and starts over with that list. The loop ends when the path is clear.

How it works, step by step:

  1. Require a destination. A move with neither field set cannot be resolved: {false, "Can't resolve a tray move with no tray id or dest"}.
  2. Start the search at the destination. The question is “which empty tray is closest to where one is needed”, so the source vertex is the destination pose ({node_id: 21, heading: -90}, B21: B21 lists heading 90 with faces_reciprocal: true, so its inbound heading is −90), not any tray. The code calls this “basically the inverse OpenSpaceSearch”.
  3. Ignore everything movable. GetStaticFilter(TRAY, gg_, working_state, table_, all trays, all agvs, {}) makes every tray and AGV transparent. Only static obstacles (disabled nodes, nodes the tray footprint cannot use) block the search, so the nearest empty tray can be found even if it is buried; the main loop will clear the way afterwards.
  4. Search. EmptyTraySearchEnvironment(gg_, table_, working_state, cost_model_, filters) treats a vertex as a goal when it holds a tray with no payload. SingleSourceSearch expands vertices by cost, so the first goal reached is the cheapest to reach, not necessarily the fewest hops. No goal → {false, "Failed to find empty tray to move to <dest>"}.
  5. Read the tray. working_state.GetTrayOnNode(node_id_of(target)) → move.SetTrayId(tray.id).
  6. Avoid pointless rotation. If the tray's heading is the destination heading or its reciprocal (IsAngleOrReciprocal) but not equal, the destination heading is changed to the tray's heading (an empty tray has no front), then UseEvChargeHeading restores the heading if the destination is an EV-charging spot that needs a specific one.

Three consequences are easy to miss:

  • Nothing is reserved. The helper does not apply the move or touch freeing_moves. T23 is “taken” only because DoTrayAssignments continues straight into the main loop and applies the move to working_state there; a later event will then see T23 in the bay.
  • Distance is measured from the bay, not from the AGV. The chosen tray is the one cheapest to reach from the destination, ignoring how many blockers sit on its path. A TODO in the code suggests preferring a tray that will be a blocker anyway.
  • The search repeats work. The main loop runs a second search (the critical path) over roughly the same ground; the source comment calls this a future optimisation.

AGV assignment: DoAgvAssignments

Now every TrayMove knows what moves where. DoAgvAssignments(ctx) decides which AGV does each one and adds the AGV's own events. It works on event_dag_copy, a copy of ctx->events that it consumes from the roots down:

  1. Drain non-tray roots. Apply every root that is not a TrayMove (bay and VECS transitions, pre-existing AgvMoves) to working_state, chain AGV moves per AGV, add node-arrival dependencies, and remove them from the copy. Repeat until only TrayMove roots remain, so the matcher sees every eligible move at once (the SW2-377 comment explains why).
  2. Cost every (AGV, root move) pair with GetAgvToTrayAssignmentCost. Pairs are infeasible when the AGV carries a different tray, has no path, or is trapped in a bay that is not READY_TO_RETRIEVE.
  3. Match with volley::BottleneckAssignment and order matched AGVs that would collide with GetEventDag.
  4. Expand each match into events and remove the matched TrayMove from the copy.
  5. Repeat until the copy is empty, then run EnsureAgvMovePathsClear, Reduce(), and AddDepsAfterAmiga for bay and VECS transitions.

The cost of assigning AGV i to tray move j is

c_{ij}=\max\!\left(t_i^{\mathrm{occupied}}-t_j^{\mathrm{ready}},\,0\right)+t_{ij}^{\mathrm{approach}}+t_{ij}^{\mathrm{lift}},

where cost c_{ij} [s] is the estimated time until the tray is lifted, t_i^{\mathrm{occupied}} [s] is how long AGV i is already busy (agv_occupied_durations), t_j^{\mathrm{ready}} [s] is the earliest time move j can start given its parents (event_occupied_durations, filled by PropagateEventCostToChildren), t_{ij}^{\mathrm{approach}} [s] is GetJustMovingCost from the AGV's pose to the tray's pose, and t_{ij}^{\mathrm{lift}} [s] is the lift-up time when the AGV is not already holding the tray. Caveat: GetAgvOccupiedDuration() returns zero (a TODO(isabel)), so the occupied term only reflects work assigned earlier in the same call.

// Where: Scheduler::DoAgvAssignments(ScheduleContextSPtr ctx) const, after BottleneckAssignment.
//   ordered_matching -> std::vector<std::pair<uint16_t, std::optional<ScheduleEventSPtr>>>: (agv id, root event)
//   working_state    -> local DiscreteGarageState advanced as events are created
for(const auto& [agv_id, root_event_opt] : ordered_matching) {
  if(!root_event_opt.has_value()) continue;                       // this AGV got nothing this round
  auto root_event = root_event_opt.value();                       // std::shared_ptr<ScheduleEvent>
  auto* tray_move = dynamic_cast<volley::TrayMove*>(root_event.get());
  const DiscreteTrayStateMsg tray = working_state.GetTray(tray_move->GetTrayId().value()).value();
  const DiscreteAgvStateMsg agv = working_state.GetAgv(agv_id).value();
  if(agv.tray_id != tray.id) {
    MoveAgvToTrayPose(agv_id, agv, tray, root_event, ...);        // AgvMove (pose) + its dependencies
    AppendAgvLiftEvent(agv_id, /*raised=*/true, ...);             // AgvMove (lift)
  }
  tray_move->SetAgvId(agv.id);                                     // edits the shared event object
  ctx->events.AddDependency(last_agv_event[agv_id], root_event);
  AddNodeArrivalDeps(tray_move->GetDest()->node_id, agv_id, root_event, ...);
  root_event->Apply(working_state);
  event_dag_copy.Remove(root_event);
  AppendAgvLiftEvent(agv_id, /*raised=*/false, ...);              // AgvMove (lower)
  PropagateEventCostToChildren(root_event, event_cost, ctx, event_occupied_durations);
  agv_occupied_durations[agv_id] += event_cost;
}

Repairing paths after assignment

This pass exists because DoAgvAssignments builds dependencies in its own serial assignment order, which can differ from the order the DAG is eventually replayed in. The source comments in MoveAgvToTrayPose describe an earlier, proactive attempt that both missed real blockers and added spurious edges.

AddDepsAfterAmiga(ctx, event, node_id) runs last for every bay and VECS transition. It moves dependencies from tray moves onto the AGV's lift and lower events: a transition that waited for a tray to arrive now waits for the lower after it, and a tray move out of the bay waits for the transition before its lift.

Reduce() and SanityCheckEvents

Back in Plan(), plan_ctx->events.Reduce() removes redundant edges (a TODO(any) notes that planning may fail without it, probably inside CHUGG). Then SanityCheckEvents(ctx) replays the DAG in topological order on a fresh copy of initial_state and checks each event before applying it:

Event Check
BayTransition the bay's ODP (operator door) area is free (GetStaticFilter for BAY_ODP)
AgvMove with a destination IsMovePossible: destination exists, is not disabled, is not occupied, and a path exists, ignoring only this AGV
AgvMove lift change only that Apply succeeds
TrayMove has a destination, and IsMovePossible with the carrying AGV and the tray itself ignored

The comment explains the motivation: “The motion planner doesn't fail in the most graceful ways”, so a cheap discrete replay catches most problems with a readable message first.

Motion planning and the response

CHUGG, the motion planner

What the name stands for: neither snapshot says. The scheduler refers to it as the class volley::Chugg in motion_planner/chugg.hpp, as “CHUGG” in log messages, and as “CHUGG v0.1” in one comment, but no comment or file in scheduler or planner_core spells the acronym out, and motion_planner itself was not supplied. Ask the motion_planner owners rather than guessing; this guide only uses the name.

What it does is clear from how it is called. Everything before it decides what must happen and in which order: the event DAG. CHUGG decides when and where along the graph: for every AGV (and every bay, VECS and VRC) it produces a timed trajectory, a sequence of motions with start and end times, such that the event order is respected and no two bodies overlap at the same time (overlap as defined by the CollisionTable, section 3).

What the scheduler's comments say about the inside (unverified, since the code is not here):

  • Safe-interval path planning. The PlanMotions comment names a SippEnvironment. SIPP (Safe Interval Path Planning, a standard multi-agent technique) searches over (pose, interval of time during which that pose is free) instead of over individual time steps, so a new motion can be routed around trajectories that are already planned.   • A fast but not optimal heuristic. The same comment says the all-pairs heuristic is inadmissible under the current “run-extension” cost (it can overestimate), so A* may return suboptimal paths; this was chosen for speed, with a tighter heuristic noted as a follow-up.
  • Its own event order. AddNodeArrivalDeps exists because “chugg's topo sort can interleave per-AGV chains and try to apply an arrival before the prior occupant has departed” (a “two AGVs at the same node” failure in InitializeEventOrder). CHUGG walks the event DAG in a topological order, so any ordering it must respect has to be an edge.
  • Sensitive to redundant edges. The TODO above the Reduce() call in Plan() suspects GetDependencyCompletionTime() inside CHUGG as the reason planning may fail without a reduction.
  • One event after another. The method is called SolveSequential, which suggests events are planned one at a time in that order rather than jointly; the name is the only evidence.

The scheduler shapes its DAG for CHUGG in three places, all covered earlier: node-arrival edges (AddNodeArrivalDeps), AGV path repair (EnsureAgvMovePathsClear), and Reduce() right before the sanity check (sections 17 and 18). A test comment adds a known limit: “CHUGG can't handle rando AGVs strewn about yet”.

Output. ContinuousState::GetTrajectories() maps each entity to its list of Motions. The response code uses these accessors: GetEntityId(), GetInterval() (start and end time), GetCollisionId() (which footprint: a bare AGV, an AGV carrying a tray of some size, ...), GetActionId() (the vertex of the event in ctx->events that the motion implements), GetSourcePose() / GetLocation(), GetDelta() (the discrete change, if the motion has one) and IsIdle(). Bays, VECS and VRCs

Bays and rebalancing

bay_readiness_ratio is the fraction of usable bays that should be ready for insert. CalculateDesiredBaySplit rounds up (it biases towards insert because arriving customers cannot be detected), clamps, and never asks for more insert-ready bays than there are empty trays. ComputeBayRebalancingActions first counts bays already moving towards a state (WILL_BE_*), then keeps bays already in a wanted state, and only then picks bays to change, in bay_prioritization order for insert and reverse order for retrieve. Bays left in an invalid state fall back to ready-for-retrieve.

VECS (EV charging)

A VECS sits on a node of type TYPE_EV_CHARGE (6, a node type of its own; its VECS id is the node id). Moving a tray off a VECS that is CHARGING first adds VecsTransition CHARGING -> READY_TO_CHARGE; moving onto one is refused unless it is READY_TO_CHARGE. PlanChargePayloadJob finds a VECS with ResolveBlockingTrays (the open-space search knows about VECS nodes) and then adds READY_TO_CHARGE -> CHARGING.

VRCs (lifts between floors)

In this package VRCs are handled at the action level, after motion planning: InsertVrcActionsIntoDag (in utils.cpp) walks AGV actions in topological order, simulates the carriage floor per VRC, and inserts a TYPE_VRC_COMMAND approach when the carriage is on the wrong floor for the AGV's next action, plus a move command that replaces each cross-floor AGV action. Each command's duration is door close + carriage transit + door open. Consecutive cross-floor motions are first collapsed into one motion in CollectAndCollapseTrajectoryMotions. VrcTransition (in planner_core, section 12) exists, but the scheduler never creates one.

FAQ: design questions

Questions new engineers ask once they have read sections 10 to 18. The answers separate what the code does (with evidence) from opinion (marked as such).

Is "events plus a DAG" a common way to model this problem?

Yes. Two established ideas are combined here:

  1. Precedence-constrained scheduling. Activities with "finish before start" constraints form a DAG. This is the standard model in project scheduling (critical-path networks) and shop scheduling. The event DAG built in job expansion is exactly this: "the bay must open before the tray goes in".
  2. Action dependency graphs for multi-robot execution. Hönig et al. (RA-L 2019) turn a time-stamped multi-robot plan into a DAG of actions. One kind of edge chains the actions of one robot; the other kind orders actions of different robots that use the same location. Robots then run at their own speed and wait only on edges, which makes execution robust to delays. Later work describes it as "a directed acyclic graph representing the temporal dependencies between actions" (Streamlining the ADG framework, 2024). The scheduler's response is close to this: ActionNode[] where each node lists its parents, chained per entity and ordered by occupancy (section 19).

What is more specific to this code base is that the DAG exists before any motion is planned and is handed to the motion planner as input (volley::Chugg motion_planner(gg_, table_, ctx->events, ...) in PlanMotions). The DAG first carries task logic (which tray must move before which) and only at the end becomes an execution policy.

Open-RMF's rmf_traffic has no DAG; it is a database updated by events. Why is this different?

The two systems solve different problems.

Open-RMF rmf_traffic This scheduler
Who plans robot paths Each fleet or participant plans its own robots One central planner plans every AGV
Shared object A traffic schedule database of timed itineraries. Participants write through schedule::Writer: set, extend, delay, reached, clear (API) A PlanRequest holding the current garage state and in-flight actions, answered with a full schedule
Conflicts Detected between itineraries and resolved by negotiation (for example rmf_traffic::agv::CentralizedNegotiation, API) Avoided at planning time: precedence edges plus collision-aware motion planning (CHUGG)
Coupling between tasks Mostly spatial: robots share corridors Strong and logical: moving one car can require moving several other trays first, an AGV must lift a tray, bays have modes
Built for Many heterogeneous fleets from different vendors in one building One tightly coupled automated garage

Two nuances:

  • Open-RMF is not entirely free of dependencies. Its routes can declare them: DependsOnCheckpoint is a map where "the checkpoint in the value waits for the checkpoint in the key" (API). That is a precedence edge between plans.
  • This scheduler is event-driven too, just one level up. Scheduler::Plan() keeps no state between calls: everything lives in a fresh ScheduleContext. The live state and the job queue are held by Dispatch, which sends base_state (the garage now) and base_schedule (actions already executing; Plan() marks their AGVs, nodes, bays and VECS disabled) with every request. "A robot went down" or "a new car arrived" therefore means a new PlanRequest, not an edit to an old DAG. Dispatch is not in the snapshot, so when exactly it replans cannot be shown here.

Why a DAG fits better here (opinion): the hard part of this garage is not two robots meeting in a corridor but chains like "to retrieve T17, first move T15 out of its way, which needs a free spot, which needs the bay to switch mode". Those are precedence constraints, and a DAG states them directly. A traffic database would still need something like it to express "this tray move must finish before that one starts".

Does a DAG and its topological order force one command at a time?

No. A DAG is a partial order. An edge u -> v only says that v may not start before u ends. Two actions with no path between them can run at the same time, and with several AGVs they usually do.

It helps to separate three things that are easy to blur: the DAG (the constraints), the topological order (one list that respects them) and the execution (what happens in time). The figure follows one small example through all three.

Read it as a pipeline:

  1. Input: one DAG, not several. The lanes are only a way of drawing it; the bay edges and the occupancy edge connect them. (Even a DAG with no edges between lanes would be fine: it would simply mean nothing waits for anything.)
  2. The topological sort produces a list, std::optional<VertexVec>. It neither creates nor removes parallelism; it only guarantees that every node comes after its parents. The scheduler uses this list to replay events on a DiscreteGarageState and to number the actions.
  3. The response keeps both the list and the edges. BuildScheduledActionsArray walks the action DAG in topological order, gives each action its position in Schedule.nodes, and fills parents from its in-edges plus the previous action of the same AGV, bay or VRC. So the "sorted graph" is exactly this: a sorted array in which every node points back to its parents, always at smaller indices.
  4. Execution is driven by parents, not by array order. A node can start as soon as all its parents are done; nodes without a path between them run at the same time. The times themselves come from motion planning: in the ContinuousStateToSchedule test, AGV 1 and AGV 2 both have motions starting at t = 0. How Dispatch's executor consumes parents is outside this package.

Parallelism is still lost wherever an edge exists. Some edges are physical (one AGV does one thing at a time; a tray is in one place). Others are choices: rule B orders every step of a job even when two steps could overlap, and REBALANCE_GARAGE runs its bays one after another because they share a job index (section 14.18). Those are fair targets for improvement.

The logic feels convoluted. Is it?

Partly. It helps to separate what the problem forces from what the code adds.

What the problem forces. Trays block each other, an AGV must fetch a tray before carrying it, bays and VECS have modes, and every job's plan depends on where earlier jobs leave things. Some precedence structure is unavoidable. Separating what must happen in which order (the event DAG) from how and when robots move (CHUGG) is a sound and common split.

What the code adds (evidence from scheduler.cpp):

  • One mutable DAG, edited by three passes. Job expansion leaves blanks (T21 -> ?), tray assignment fills them and adds blocker moves, AGV assignment adds approach, lift and lower events. To know what an event looks like you need to know which pass you are in.
  • Edges come from many places. AddDependency appears 28 times in scheduler.cpp, spread over ten Scheduler methods (DoTrayAssignments 7, AssignDestForUntargetedMove 5, MoveAgvToTrayPose 3, PlanReparkTrayJob 2, DoAgvAssignments 2, AddDepsAfterAmiga 2, and one each in AppendAgvLiftEvent, AddNodeArrivalDeps, GetEventDag and TryClearBlockedAgvMove), plus the two ScheduleContext helpers. An edge does not record why it was added, and Reduce() later removes the redundant ones, so the final DAG does not show where its edges came from.
  • Repeated replay. Almost every step copies initial_state and replays the whole DAG to know the current state.
  • Implicit conventions. job_index is a position in a list that only successful jobs enter; failed jobs can leave events behind (section 14.18).

What would make it easier to follow (suggestions, not plans): record a reason or kind on every edge; keep each kind of constraint in one function; check invariants after each pass (acyclic, every TrayMove complete, no leftover events); give each pass a narrow input and output. That last point is what the solver interfaces in 02 start to do. Until then, the debug/printdags service (section 22), which logs the DAG after each pass, is the best way to see what the code built.

Does the code really call them rule A, rule B and rule C?

No. The letters are this guide's shorthand, chosen to keep the figures readable. Search the code for these names instead:

Rule A ScheduleContext::UpdateLastEntityEvent(entity_id, new_event) in scheduler.hpp, using the map last_entity_event "Add a dependency on the entity's last event, if it had one"
Rule B ScheduleContext::UpdateLeafDependencies(child, job_index) in scheduler.hpp "Adding a new child event to the leafs in the DAG. Each leaf becomes a parent to the new child event."

Why each one is needed, by what would go wrong without it:

  • Without rule A, two jobs that touch the same tray, AGV, bay or VECS would be unordered. If job 0 moves T19 from P19 to P24 and job 1 moves it from P24 to P23, nothing would stop the replay, or the robots, from doing job 1's move first, starting from a place the tray is not at yet.
  • Without rule B, the steps inside one job would be unordered: the car's tray could be planned into B21 before the bay switches to retrieve mode, or PROCESS_RETRIEVE could run before the tray arrives.
  • Without rule C, a tray could enter a bay before an earlier job's bay event finished. Rule B does not help across jobs, and rule A does not either, because a TrayMove is chained to its tray, not to the bay it enters. For example, a READY_FOR_INSERT job bringing an empty tray into B21 must wait for the previous job's PROCESS_RETRIEVE on B21; only rule C adds that edge.

The three rules are not the whole story. They only order what the job methods know about. Geometric conflicts (a tray in the way, two AGVs on one node) are turned into edges later by tray and AGV assignment (sections 16 and 17).
