09 — Simulation: running the real stack against a simulated garage

A simulation runs the whole garage software on one layout file, with simulated patrons, bay hardware, AGVs and time. This tab starts from the layout (the Layout file tab) and builds up: which sites the layouts describe, what the launcher starts for a layout, what a scenario adds, how to run and record a simulation, how to test with it, and how to use it to show that the refactor changed nothing.

The Verification tab checks the scheduler one stage at a time, on hand-built fixtures (section 2). A simulation run is the opposite end: every node except the hardware is the production node, the garage state evolves over many plan calls, and the scheduler sees the requests Dispatch really builds. It catches what fixtures miss, and it produces realistic plan calls that can be replayed against the refactored code.

From a layout to a simulated site

The Layout file tab describes the map: nodes, edges, parking windows, floors and VRCs (section 2). A simulation adds three files around it, all found by name:

  • The scenario (scenario/scenarios/<name>.yaml) names the layout, puts AGVs and trays on its node ids, may override node parameters, and lists timed set-up events.
  • The installation parameters (launcher/params/installations/params_<layout>.yaml) hold the site's hardware settings: IO-link masters, the bay's sensor box, the load-cell scale, the BLift floor specification. On site the file is required; in simulation it is optional.
  • An events file (optional, also in scenario/scenarios) holds the workload: retrieves, patrons, moves. It has no layout of its own and is fed into a running simulation by a second process (section 4.2).

The launcher (launcher/sim_nodes.py) takes the layout name from the scenario and uses it everywhere: it loads params_<layout>.yaml, sets the layout parameter of every node, and builds the machine nodes from the layout object:

In the layoutWhat the launcher starts
Each Bay node bContainer sim/b<b>_nodes with /bay/b<b>/bay_state_machine, vehicle_estimator, bay_guidance (the real bay nodes) and bay_sim (the simulated hardware)
Each BLift nodeThe same, with bay::BliftStateMachineComponent instead of the standard machine, plus vrc_lift_bridge, which maps the VRC's report and move topics to the bay's lift topics. The launcher fails if the BLift is not listed in a vrcs entry

Because the launcher takes the layout from the scenario, the simulator, the garage tracker, the scheduler and the visualizer always run on the same file, and the consistency monitor's checksum comparison cannot fail on a layout mismatch.

The Pecos test facility as three layouts

The Pecos YAML used throughout this pack (5675_pecos_combined.yaml) has two sections, marked by comments: 5675_pecos_sandbox_eng (bay B7, stalls P2, P3, P5, P6, charger C10) and 5675_pecos_sandbox_qa (bay B21, six stalls from P15 to P24, chargers C14 and C16). They are joined by the single edge W8–W13 (section 5). The scenarios use three layouts: each sandbox alone and both together, with the same node ids. The names suggest an engineering area and a QA area on the same test floor.

The installation parameters of the three sandboxes differ in the hardware only: the IO-link master addresses are swapped between sandbox_eng (master 1 at .60, master 2 at .62) and the other two, sandbox_eng has a 5 kN load-cell scale (0.001), and all three set the bay's sensor box to 5.791 m × 2.2098 m (the XL parking window's length). 5675_pecos_bench has an empty parameter file and no scenario in the snapshot.

Two kinds of site: a bay at grade, and a bay on a VRC

Pecos is a single floor: the customer bay is one node of the parking floor. The New York sites are different. At 38 Gramercy the bay is a BLift: its tray carriage is also a VRC stop, so the patron leaves the car at the street-level motor court and the VRC lowers the tray to the parking floor. 360 W Broadway has a BLift floor specification too. The launcher handles both kinds by node type.

For the refactor this matters in one way: a BLift scenario is the only kind that drives the VRC code paths of the scheduler end to end. Their layouts are not in the snapshots, so no BLift scenario could be read.

What is real and what is simulated

  • Real: the dispatcher, the garage tracker and the monitors (central), the scheduler, the bay state machines, vehicle estimators and guidance (bay), the VECS manager, and the REST API. They are the same code as on site; the dispatcher calls /scheduler/plan and executes the response as usual (Dispatch tab, section 3).
  • Simulated: patrons (arrivals, inserts, pick-ups), the bay, VECS and VRC hardware, the AGVs, the passage of time, and the operator actions written into the scenario or an events file (retrieve requests, tray moves, disabled nodes, ...).
  • Shared timing: params.yaml gives the lift durations (6 s up, 6 s down) once, as the "shared source of truth between the scheduler's cost model and the AGV sim". Drive speeds and accelerations (agv.performance_limits) are in the same file. If the simulated AGV uses them as the cost model does, simulated job durations match the planner's estimates by construction, so a simulation cannot reveal a wrong cost model, only a wrong plan.

Because the scheduler is untouched by the simulation, any difference in a simulated run between the old and the refactored scheduler comes from the scheduler, or from timing (section 6.3).

Processes and containers

  • The clock runs in its own process, on wall time, "to minimize lost-wakeup stalls"; every other node has use_sim_time true.
  • If the clock process or the sim_nodes container exits unexpectedly (for example on a collision, section 3.4), the launch shuts everything down.
  • All /rosout output of the sim nodes, bays and central container is remapped to /sim/rosout, /central/rosout or the node's own namespace.
  • ROS_DOMAIN_ID defaults to 75 and GITSHA to unknown (for the consistency monitor) if they are not set.

Simulated time

SimClockRos keeps a simulated time and, on a wall-clock timer every clock_publish_period_ms (5 ms), advances it by 5 ms × real_time_factor and publishes it on /clock. Every node started with use_sim_time follows it, so all timers in the stack, including the dispatcher's 850 ms planner timer and the simulator's 50 ms update, run in simulated time.

  • real_time_factor:=4 on the launch command runs four times faster; 0 pauses the whole stack. It can be changed while running: ros2 param set /sim/clock real_time_factor 0.
  • The scheduler's planning time is wall time. At high factors a plan call takes proportionally more simulated time, so job durations measured in simulated time grow with the factor. Fix the factor when comparing runs.
  • At factors above 10, each /clock message advances time by more than the simulator's 50 ms update period. Check that the timers still fire as often as expected before trusting results at such factors.
  • The event runner of section 4.2 runs on wall time: its sleep event and its 1 s polling do not scale with the factor.

Figure 6 follows a run from start to end. Everything the simulator does happens in Simulator::Update, every 50 ms of simulated time.

Seeding and the scenario clock

The first updates seed the garage tracker. SimClients::ProcessInitialConditions waits until /central/add_agv, add_tray and add_payload are available, then calls them (blocking) for every AGV, tray and payload of the scenario; a failed call throws and stops the simulator. add_agv receives only the id: the AGV's pose comes from its SimAgv node, which the launcher started at the scenario's garage_pose. Until seeding succeeds the update does nothing else.

The scenario clock starts at the first update in which /central/report says Dispatch is STATUS_STOPPED and consistent. Event times are seconds after that moment, so the same scenario lines up the same way whatever the start-up takes. Dispatch is stopped at that point, so a scenario normally starts with set_dispatch_mode and start_dispatch events.

Events become service calls

The ScenarioRunner holds the events in a priority queue by time. On each update, GetNextEvents returns every event due by now, and HandleEvents sends one service call per event. The same events also arrive at run time through /sim/enqueue_garage_event (section 4.2).

The two planner events are the useful ones for testing the scheduler: set_auto_planner: false followed by call_planner events makes plan calls happen at chosen moments instead of every 850 ms.

Patrons and the simulated bay

A patron_arrival event puts a payload at the back of the simulator's insert queue (a queue without duplicates). Every update, OfferWaitingPayloadsToBays offers the payload at the front to each bay through /bay/b<N>/sim_offer_inserting_payload. A BaySim accepts only when its bay reports READY_TO_INSERT and no insert is in progress; the first bay that accepts takes the patron.

BaySim::Tick (every 50 ms) then plays the patron and the hardware:

  • Load cells show the tray's mass, plus the vehicle's mass in proportion to the axles on the tray while the patron drives on (the tire sensor is briefly "broken" to model the wheels crossing it).
  • Vehicle proximity sees the patron; the radar is always valid and clear; the doors are simulated by GarageDoorSimRt with the configured open and close times.
  • Insert: with auto_confirm_insert (the default; launch argument auto_confirm_insert:=false turns it off), the sim calls the bay's confirm_insert with the patron's dimensions when the insert machine reaches VEHICLE_INSERTED; otherwise it waits for an external confirmation (the app, the REST API or scripts/confirm_insert.bash). The bay then reports the insert and Dispatch creates the INSERT job.
  • Retrieve: when the retrieve machine runs and the doors on the current floor are closed, the sim calls confirm_retrieve once; when the patron door opens, the vehicle is assumed to leave at once (its mass disappears from the load cells).

Collision checking

Every update, RunCollisionCheck rebuilds a 3D box for every AGV, tray, payload and bay from the latest /central/garage_snapshot; chargers and the scenario's obstructions are registered once. CollisionDetector::FindCollisions tests every pair: two boxes collide when the separating-axis test finds no separating face normal and their height bands overlap.

An AGV and a tray whose centres are within 0.15 m in x and in y count as "carried" and are not reported. This also covers the QA sandbox's start, where both AGVs stand lowered under trays. Any other overlapping pair ends the run: the simulator logs RCLCPP_FATAL with the pair, for example Collision: a3 collided with t17! (a = AGV, t = tray, p = payload keyed by its tray, b = bay, c = charger, o = obstruction), and calls rclcpp::shutdown(), which stops the launch.

This check is independent of the planner's own collision model (the collision table and footprints of the Motion planning tab). It sees the poses the machines actually report, so it catches a plan that is unsafe in execution, not only in planning. It sees them only every 50 ms of simulated time, from snapshots, so a brief overlap between two updates can be missed.

What the simulator reports, and how to watch a run

  • /sim/report (SimReport): running, num_remaining_events and the payloads still waiting to be inserted.
  • RViz and Foxglove (both started by default), through the visualizer's marker topics: agvs, agv_commands, trays, payloads, bays, vrcs, the layout topics (nodes, edges, layout_spaces, ...), request_markers (the retrieve and insert queues) and schedule_dag, which draws every AGV command of the latest /central/schedule.
  • The central topics: /central/report, the pending, active and completed job lists, and the plan request and response topics (section 5.4). The metrics_recorder node turns the job lists into job pending and active durations.

Scenario files and events files

The scenario package holds two kinds of YAML file in one folder, scenarios/, and installs them all to share/scenario/scenarios:

  • A scenario file has a layout key. It is what the launch command takes; the simulator fires its events at their times.
  • An events file has only events. It is fed into a running simulation, one event at a time, by exercise_sim_events.

The scenario file

The file is read twice: by the launcher in Python (common_py.scenario.load_scenario and load_initial_conditions), which needs the layout, the AGVs and the parameter overrides, and by the simulator in C++ (ParseScenarioFile), which needs the trays, payloads, obstructions and events. Required fields are read without checks: a missing one throws and the run does not start.

Events files and the exerciser

ros2 run scenario exercise_sim_events -l <layout> -e <events file> [-o <csv>] starts a node, sim_event_exerciser, next to a running simulation. It waits until /central/report says Dispatch is RUNNING, then runs the file's events in order, each after the previous one is handled, and sends each one to /sim/enqueue_garage_event with time 0, so the simulator fires it on its next update.

  • Optional on every event: wait_for_job_completion: true makes the event count as handled only when its job is SUCCESS or ERROR.
  • Job attribution: before each event, a SchedulerJobTracker notes the jobs of the event's type already in the dispatch report; the first new job of that type is taken as the event's job.
  • End: after the last event, when every tracked job has finished, the exerciser writes one CSV row per event (sim_metrics; default /tmp/sim_results/events_summary.csv), sends SIGINT to the other ROS processes, and exits with status 0, or 1 if any job ended in ERROR or an exception occurred.

This is the closest thing to a pass or fail the stack has: an events file run headless gives an exit status and a metrics file per run.

The per-site scenario family

Each site with standardized tests gets the same set of files: start files and events files that pair up. The Pecos sandboxes follow this pattern, and so does 275_sunrise_b.

Two settings in the start files are chosen on purpose. bay_readiness_ratio is 1.0 when the garage starts empty, so that every bay is made ready for a patron, and 0.0 when it starts full, so that the scheduler does not spend AGV time preparing bays for inserts that will not come. The auto planner is switched on at 5 s, after Dispatch has started in automatic mode at 1 s.

Batch configurations

batch_configs/*.yaml group runs: a batch_name to group results, a layout and layout_version, one start scenario, and a list of events files. The three 550_w21st batches start a full garage (14, 15 or 16 vehicles) and retrieve each vehicle in turn, one events file per stall; the two standardized tests run fill_and_drain three times on the engineering and the QA sandbox, with batch_name: release-26.XX to be replaced by the release under test.

The program that reads these files is not in the snapshots, and setup.py does not install batch_configs/. The launcher is ready for it: get_sim_launch_description accepts a scenario, an artifacts directory and base name, parameter overrides and a real time factor as Python arguments, and returns the layout, the initial conditions and the scenario's events along with the launch entities.

Driving a run

ros2 run scenario exercise_sim_events -l 5675_pecos_sandbox_qa \
  -e 5675_pecos_sandbox_qa_events_drain_from_full -o runs/qa_drain.csv   # the workload; exits 0 or 1
ros2 service call /sim/enqueue_garage_event interfaces/srv/SimEvent \
  "{type: 'retrieve_request', time: 0.0, payload: {id: {bytes: [...16 bytes...]}}}"   # one event by hand
scripts/trigger_patron_arrival.bash             # a patron with a random GUID
ros2 param set /sim/clock real_time_factor 0    # pause; 1 resumes
ros2 topic echo /sim/report                     # remaining events, waiting patrons
ros2 topic echo /central/report                 # dispatch status, mode, consistency

A run ends when the launch is stopped, when the exerciser finishes (it stops the other ROS processes), or by itself on a collision.

Recording a run

record_artifacts:=true adds a recorder (rosbag2_transport, node /sim/recorder, on simulated time) that records every topic (regex: .*) into one mcap file set, compressed with the zstd_fast preset and not split, in <artifacts dir>/<UTC timestamp>/sim. Topics that appear later are picked up as well.

The recording therefore includes what a replay of the scheduler needs: Dispatch publishes every request it sends to /scheduler/plan and every response it receives on two topics, explicitly "to be bagged" (DispatchRos::CallPlanner), alongside the job lists, the reports, the scheduler's report (which carries the current bay_readiness_ratio) and /clock. To look at a recording again:

ros2 launch launcher bagplay.launch.py bagfile:=~/.ros/artifacts/20261013T120000Z/sim
# plays the bag in a loop with the visualizer and the Foxglove bridge

Determinism, and what to compare

Two runs of the same scenario do not produce the same plan calls. Timers in different nodes fire in different orders, service calls are asynchronous, the real time factor stretches planning time differently, the exerciser polls on wall time, and AGVs finish actions at slightly different simulated times. A job that arrives 50 ms later may land in the next plan call. Comparing two closed-loop runs request by request therefore shows differences even when the scheduler is unchanged.

So the comparison is split. The scheduler is compared on identical inputs: the plan calls recorded in one run, replayed offline (section 7.1). The system is compared statistically: outcomes and durations over repeated runs (section 7.2).

Checking the refactor with the simulator

The existing families give a ready-made baseline set: for each Pecos layout, fill from empty and drain from full, run with record_artifacts:=true and the exerciser, at a fixed real_time_factor. Together with the 550_w21st batches and exercise_576_eccles, that covers three sites, both directions of traffic and garages up to 27 trays.

Replay recorded plan calls

The scheduler is a function of the request, the time and its parameters (Background tab). A recording from a baseline run holds the requests and the responses; a test can feed each recorded request to the old and the new Scheduler::Plan and compare the two results with the canonical comparison of the Verification tab (section 4). This adds to the hand-built fixtures in three ways: the requests are real (states left by earlier jobs, several pending jobs, disabled nodes); there are many of them; and they cover what Dispatch actually sends, including base_state fields the fixtures never set.

// PROPOSED — test/replay_plan_calls_tests.cpp (sketch; reads a recording made with record_artifacts:=true)
// layout / params : those of the recorded run (same layout file, bay_readiness_ratio from the scheduler report)
volley::Scheduler old_scheduler(layout_path, logger, params);      // baseline commit, built from a pinned copy
volley::Scheduler new_scheduler(layout_path, logger, params);      // refactor branch: Plan() through the solvers
for(const auto& [stamp, request, recorded] : ReadPlanCalls(bag_path)) {   // pairs matched by request id
  const PlanResponseMsg old_response = old_scheduler.Plan(request, stamp);
  const PlanResponseMsg new_response = new_scheduler.Plan(request, stamp);
  EXPECT_EQ(Canonical(old_response), Canonical(recorded)) << "replay is not faithful";   // sanity check
  EXPECT_EQ(Canonical(new_response), Canonical(old_response)) << "behaviour changed";
}

Notes for the test:

  • The old scheduler must run in the same test, or its canonical outputs must be stored. Both binaries are the same package at two commits; the simplest route is to compare new against recorded (the old responses are in the recording already), keeping the old-replay check for the baseline commit only.
  • Time: Plan takes now; use the recording's receive stamp of the request in simulated time, the same for both schedulers.
  • Parameters: set_bay_readiness_ratio changes the scheduler between calls, and a scenario's params: block may change others. Record the scheduler report, keep the scenario file with the recording, and set the ratio before each replayed call.
  • Canonical form: compare the action DAGs by content and reduced edge sets, and the ScheduledJobData list by job, never by GUID or index (Verification tab, section 4).
  • Gate: the pass ratio p over all recorded calls must be 1, exactly as for the fixtures.

Replay is deterministic and needs no ROS graph, so it can run in CI on every pull request. The recordings become part of the benchmark set: their requests can be timed with the method of the Verification tab (section 5).

Closed-loop runs

Replay checks the scheduler on the baseline's requests only. If the refactor changed a decision, later requests in a live run would differ, and replay alone would not show the consequence. Closed-loop runs on the candidate check that the system still behaves. For scenario s and run r\in\{1,\ldots,R\}, where R\in\mathbb N is the number of runs, record:

  • whether any collision occurred (must be never);
  • the exerciser's exit status and the outcome of every job, SUCCESS or ERROR with its error class (must match the baseline runs);
  • the makespan M_{s,r}\in\mathbb R_{\ge0} [s]: simulated time from the scenario start until no job is pending or active;
  • for each retrieve, the time from request to hand-over [s], and its median W_{s,r} over the run (the exerciser's CSV has one row per event).

Let \widetilde M_s and \widetilde M_s^{(0)} be the medians of the makespan over the runs of the candidate and of the baseline. The relative change \Delta_s\in\mathbb R is:

\Delta_s=\frac{\widetilde M_s-\widetilde M_s^{(0)}}{\widetilde M_s^{(0)}}.

For a parity refactor the expected value of \Delta_s is 0; accept it when |\Delta_s| stays within the spread of the baseline's own runs, measured beforehand with the same real time factor. The same rule applies to W. A change outside that spread, with the replay passing, points at timing rather than decisions: investigate before merging.

Gaps and proposed improvements

Found while reading the packages. None blocks the refactor; the first four matter most for using the simulator as a test.

  • The simulator has no pass or fail. A run ends on a collision or when it is stopped; only the exerciser gives an exit status, and only for the jobs it tracked. Proposed: an optional expect block in the scenario (jobs that must succeed, a time limit, allowed errors) checked by the simulator, which then exits with a status code.
  • Some events files use event types the exerciser does not know. All *_events_move_each_node files, tiny_lot_events_fill and events_insert_retrieve use wait_for_any_non_busy_agv, wait_until_previous_completed, wait_for_next_bay_ready_to_insert or done_events_wait_jobs_end_simulation, and fields sleep and time it ignores. The exerciser raises "Unknown event type" and exits with status 1. Proposed: convert them (most map to wait_for_job_completion and sleep events), or delete them, and add a test that loads every events file through the exerciser's registry.
  • The standardized batches refer to a missing file. pecos_sandbox_eng.yaml and pecos_sandbox_qa.yaml list *_events_fill_and_drain three times; no such file is among the scenario files. Proposed: add the file (fill then drain), and a test that every name in a batch configuration resolves.
  • Events due in the same update run in reverse order. GetNextEvents returns the due events oldest first, and HandleEvents takes them from the back, so the newest runs first. The start files hit this: set_dispatch_mode and set_bay_readiness_ratio both at 0.5 s fall in the same update. Events with equal times have no defined order at all (a std::priority_queue is not stable). Proposed: process in time order, then in file order.
  • Service results are not checked by the simulator. Most events use CallAsync, which reports only that the request was sent. A refused retrieve leaves no trace in the simulator (the exerciser does check the SimEvent answer). Proposed: log or count failed responses in /sim/report.
  • Battery state is not simulated from the scenario. battery_fraction in agvs[] is parsed but neither the launcher nor the simulator passes it on, and set_agv_battery_fraction is logged as not implemented. charge_then_repark.yaml depends on both, so it does not test what its comments describe.
  • The exerciser stops every ROS process on the machine. end_simulation sends SIGINT to every process whose command line contains ros-args, not only to the simulation it ran against. Proposed: stop the launch it belongs to (a process group or the launch's PID).
  • Launch arguments are parsed by hand. A misspelled argument (realtime_factor:=4) is ignored without a warning, and --show-args lists nothing. Proposed: declare them as launch arguments.
  • One scenario file, two parsers. The launcher (Python) and the simulator (C++) each read part of the file; a field one adds can be ignored by the other, as agvs[].garage_pose is by the simulator. Proposed: one schema, checked by a test against every file in scenarios/.
  • In YamlToEvent, the SET_AUTO_PLANNER case has no break and falls into the cases without parameters. Harmless today; add the break.
  • A collision leaves only a log line and shuts the process down (TODO(SW2-306)). Proposed: publish the colliding pair, the time and the last snapshot before shutting down; with record_artifacts the recording then shows the moment.
  • Collision bodies are not published. CollisionDetector::ConstructBodyMessages exists and the visualizer defines a collision_bodies topic name, but nothing publishes it. Publishing it would show the boxes in RViz and Foxglove.
  • Start files without set-up events. clean_garage_unstashes_waypoint_tray, repark_tray, payload_starts_in_bay and try_odp_agv_collide_bay_outbound_node have events: [], so Dispatch never starts unless someone starts it. If they are meant for automatic runs, add the four set-up events of the families.
